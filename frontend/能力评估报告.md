# SimpleAgent2_Cycle 能力评估报告

测试日期：2026-09-25
模型：qwen2.5:7b（编排与执行同一模型）
回退后端：snapshot（本机未装 git）
判定方式：`verify_command` 退出码，调用方提供、模型不可改写

## 一、结论：当前可用层级

**能可靠完成的：单文件 / 单函数 / 无异常语义 / 无 I/O 的确定性任务。**

| 级别 | 任务 | 结果 | 尝试 | 任务数 | 耗时 |
|---|---|---|---|---|---|
| L1 | 单文件 / 单函数 | ✅ PASS | 1 | 1 | 4.6s |
| L2 | 单文件 / 控制流 + 边界 | ❌ FAIL | 3 | 2 | 62.2s |
| L3 | 单文件 / 递归 + 输入校验 | ❌ FAIL | 3 | 2 | 148.8s |
| L4 | 单文件 / 类 + 异常语义 | ✅ PASS | 1 | 1 | 5.4s |
| L5 | 多文件 / 跨模块 + 算法 | ❌ FAIL | 3 | 6 | 300.7s |
| L6 | 单文件 / 文本解析 + 聚合 | ❌ FAIL | 3 | 2 | 55.8s |
| L7 | 单文件 / 文件 IO + JSON | ❌ FAIL | 3 | 4 | 161.2s |
| L8 | 多文件 / 大程序 + 多步规划 | ❌ FAIL | 3 | 4 | 172.4s |

通过率 2/8。边界**比预期低**：L2（FizzBuzz 级别的控制流）就已经过不去。

## 二、关键前提：先修掉了「模型自己改验收标准」

第一轮测试时 L2/L3 显示 PASS，第二轮同样的任务变成 FAIL。原因是发现了
`Orchestrator` 的一个缺陷：模型每轮都能用自己输出的 `verify` 字段
**覆盖调用方指定的验证命令**。

- L3 原本「PASS」是因为模型把验收断言改成了
  `assert isinstance(factorial(-1), ValueError)` —— 一个永远不可能成立的断言，
  所以它其实一直没过，只是当时看起来像过了。
- 修掉之后（调用方的 verify 不可改写），L2 从「PASS」变「FAIL」，
  L4 从「FAIL」变「PASS」。

**所以本报告的数据才是可信的。修复前的所有通过率都不可参考。**

## 三、失败根因分类

### 类型 A：逻辑/契约理解错误（L2、L3、L6）—— 纯模型能力问题

| 级 | 症状 | 证据 |
|---|---|---|
| L2 | 把「返回字符串」写成「打印到 stdout」 | `AssertionError: None`（函数无返回值） |
| L3 | 负数分支未抛异常，静默返回 | `AssertionError: 负数未抛 ValueError` |
| L6 | 大小写折叠/计数错误 | 期望 `[('the',3),('bird',1)]`，实得 `[('the',2),('cat',1)]` |

这三类**迭代也无法根治**，只能靠更强模型或更明确的规格描述。
共同点是：任务描述里已经写清了语义（"返回"、"抛出 ValueError"、"转小写"），
模型仍按自己的直觉实现。

### 类型 B：把 Agent 工具当成 Python 函数（L8）—— 概念混淆，值得单独处理

L8 产出的 `storage.py`：

```python
def save(path, data):
    write_file(path, data)      # ← write_file 是 agent 工具，不是可调用函数

def load(path):
    return read_file(path)
```

`write_file` / `read_file` 是 agent 的工具（通过 tool_call 调用），
模型却当成了普通 Python 函数直接调用。这会导致生成代码必然跑不通。

### 类型 C：文件清单失控（L5、L8）—— 架构缺陷，最值得修

L8 最严重：任务要求产出 3 个文件，实际结果——

| 期望文件 | 实际 |
|---|---|
| `storage.py` | 存在，但内容调用虚构函数 |
| `contacts.py` | **从未被写出** |
| `cli.py` | 存在，但 `def run()` 签名错误（缺 `args`），内容是 `print(storage.__doc__)` |

而编排器在总结里**声称**三个文件都建好了。验证因此报
`ModuleNotFoundError: No module named 'cli'`（`contacts.py` 缺失导致导入链断裂）。

**根因**：系统没有「本轮应该产出哪些文件」的显式模型。验证阶段的文件清单
只能靠 `memory.artifacts` 里散落的 `write_file` 产物拼出来，
如果某个文件压根没写，它就不在清单里，验证自然也不会去检查它是否存在。

这解释了 L5/L7 的多文件失败模式（L5 跑了 6 个任务、耗时 300s 仍未收敛）。

### 类型 D：函数签名漂移（L7）

`TypeError: load() takes 0 positional arguments but 1 was given` ——
明确要求 `load(path)`，模型定义了无参版本。属于规格遵循问题，
但比类型 A 更容易通过「让验证错误更醒目」来改善。

## 四、观察：模型行为模式

从日志可稳定观察到几个 7B 的行为特征，对后续调优有用：

1. **改口不改逻辑**：同一轮里反复 `write_file` 重写同一文件，
   内容基本相同但描述措辞变化 → 指纹去重失效，靠验证回流才刹住。
2. **把「运行无报错」当成「逻辑正确」**：`run_python` 返回
   `{"ok": true, "output": "（无输出）"}` 时，模型会宣称"验证通过"。
   这是之前假成功的来源之一。
3. **同时发起多个 tool_call**：日志里常见一次返回 2 个调用
   （`read_file` + `write_file`），其中 `write_file` 可能被同一轮内后一次写覆盖。
4. **空响应**：L4 出现过连续 3 次空响应（`max_tokens` 截断或生成异常），
   直接判 `FAIL` 并烧掉一个任务。

## 五、修复优先级建议

| 优先级 | 项目 | 理由 |
|---|---|---|
| P0 | **文件清单（manifest）机制** | 类型 C，是 L5/L7/L8 的共同根因；没有它，验证覆盖不到"该有但没有"的文件 |
| P1 | `storage.py` 之类的工具/函数混淆 | 类型 B，属于低成本可拦截（在 worker prompt 里明确区分） |
| P2 | 验证失败信息在重试时更醒目 | 类型 D，现在是单行 detail，模型不易定位 |
| — | 类型 A（逻辑错误） | 属模型能力上限，迭代收益低，建议直接用更强模型 |

## 六、边界一句话总结

> 当前系统能自动、可靠地完成 **"写一个自包含的、无外部契约的纯函数文件"**。
> 一旦任务涉及 **异常语义 / 返回 vs 打印的区分 / 多文件协作 / 文件 I/O**，
> 7B 就会在 2~6 个任务内耗尽 3 次尝试并回退。
>
> 好消息是：**门禁与回退完全正常工作**——所有失败都被正确判为
> `phase=failed` 且 `rolled_back=True`，没有一次把错误结果当成成功交付。
> 这正是接下来能安全提升难度的前提。

# 一轮编码流程（CodingCycle）契约

> **同步至 CHANGELOG §36** —— 本文只描述**当前状态**；修复过程见 `docs/CHANGELOG.md`。

本文锁定二轮架构里「一轮编码流程」的接口与纪律。后续的工具插件化、结构化上下文压缩、
存储落库都建立在这个契约之上，改动这里等于改动全局，请先讨论再动。

## 1. 为什么需要这一层

旧流程（`Orchestrator.run`）的问题不是缺能力，而是**缺校验**：

- 任务是否完成，由子模型的自然语言自述决定（`worker.py` 里输出非空文本即 `ok=True`）。
  模型说「我做不到」和「已完成」在流程眼里没有区别。
- 编排器据此把 `[OK]` 写进记忆，再拿记忆做后续决策 → 假成功会污染整条链路。
- `check_syntax` / `run_lint` / `parse_python_error` 三个工具虽然实现了，但提示词里
  从未提及，属于「存在但没接入流程」。

所以这一层的核心目标只有一个：**让「完成」变成机器可判定的，而不是模型自称的。**

## 2. 五个阶段与门禁

```
PLAN → WRITE → CHECK → VERIFY → RECORD
 ↑                          │
 └────── 验证结论回流 ───────┘   （在编排循环内部，逐轮判定）
```

| 阶段 | 谁执行 | 门禁条件 | 不通过时 |
|---|---|---|---|
| PLAN | 模型（编排器） | 产出至少一个可执行任务 | 记为 failed |
| WRITE | 模型（子循环） | 产出 `write_file` 文件产物 | 记为 failed |
| CHECK | **程序** | `check_syntax` 全通过（阻塞）；`run_lint` 仅提示 | 回退 + 重试 |
| VERIFY | **程序** | `verify_command` 退出码 == 0 | 回退 + 重试 |
| RECORD | **程序** | 打检查点、返回通过 | — |

关键点：

- **CHECK 未通过不允许进入 VERIFY**，语法都不对就没必要执行。
- **VERIFY 的唯一判据是退出码**。`verify_command` 必须是一段可运行的 Python，
  用 `assert` 表达验收条件。自然语言描述的验证方式一律拒绝
  （缺少可判定命令时 cycle 直接记 failed，不判成功）。
- `run_lint` 在 ruff 缺失时返回 `ok: null` + `skipped`，表示**未执行**而非**通过**。
  旧实现返回 `ok: true` 会让模型误以为 lint 干净。

## 2.1 验证结论回流（重要）

早期实现里，验证只在编排循环**结束后**跑一次，导致一个结构性缺陷：
主循环在循环内部**不知道目标有没有达成**，只能靠猜，于是反复制造
「再运行一遍确认一下」的任务，直到耗尽 `max_rounds`。

实测日志（`sum_1_to_100` 任务）显示：同一个「运行并检查输出」动作被重复了 5 次，
两次尝试合计 17 个任务、109 秒，而有效工作只是写一个 6 行文件。

现在验证回流到循环内部，机制如下：

1. 每轮任务执行完后，若有**新的文件产物**，就用 `verify_command` 判定一次。
2. 判定结果写入 `SharedMemory.verify_state`，并在下一轮 prompt 末尾渲染成
   「【验证结论】」段落（放在最后，因为那是模型下一步行动的直接依据）。
3. **一旦通过，立即返回 `status=done`**，不再制造任何新任务。
4. 判定未通过时，把结构化错误（`error_type` + message）注入结论段落，
   引导模型定向修复，而不是盲目重试。

两个防抖细节：

- `verify_fingerprint` = hash(验证命令 + 待验证文件)。它**只与「验什么」有关、
  与历史任务无关**，所以主循环重复制造同一个验证任务也不会重复触发验证。
- 无文件产物时不做验证（没东西可验），但要与「cycle 级目标文件为空」区分开。

这也顺带缓解了 `_should_skip` 指纹去重失效的问题：即使主循环把同一个动作
换一种措辞再提一次（实测描述措辞每次都不同，指纹认为它们是不同任务），
验证也不会被重复执行。

## 2.2 验收标准的权威性（踩过的坑）

**调用方给出的 `verify_command` 是权威的，模型不得改写。**

早期实现里，主循环每轮都能用自己输出的 `verify` 字段覆盖调用方指定的验证命令。
这个缺陷在难度阶梯测试中造成了两级“假失败”：

调用方给的验证要求是「负数必须抛 ValueError」：

```python
try:
    fact.factorial(-3)
    raise AssertionError('负数未抛 ValueError')
except ValueError:
    pass
```

模型把它改写成了：

```python
assert isinstance(fact.factorial(-1), ValueError)
```

这个断言**永远不可能成立**——`factorial(-1)` 会抛异常，不会返回任何值供
`isinstance` 判断。于是模型无论实现得多正确，门禁都判失败，白白耗尽重试次数。

现在 `Orchestrator` 只在调用方**没有**提供验收标准时，才采纳模型自拟的 verify。

这条纪律的意义超出这个 bug 本身：**验收标准不能由被考核方定义**，否则整个
校验层的意义就被消解了。遗留风险与后续角色扩展的约束见 §11.3。

## 3. CycleReport：可观测契约

每个 cycle 产出 `CycleReport`（`backend/core/cycle.py`），字段即对外契约：

```python
cycle_id, goal, phase, transitions, attempts,
check_steps, verify, touched_files, commit, rolled_back, error
```

这是后续落盘（本地 / 数据库）的**最小记录单元**，也是回退关联的凭据。
`phase == "record"` 是「本 cycle 通过」的唯一标志。

## 4. 回退策略

三条纪律：

1. **git 命令绝不出现在模型可见的工具里。** 模型只能「申请检查点」，
   命令由程序生成。7B 对 `reset --hard` 的语义理解不可靠。
2. **每个 cycle 一个检查点**：cycle 开始打 baseline，通过后打正式提交；
   未通过则回退到 baseline，避免错误实现被后续任务当作「已有产物」继承。
3. **重试必须带失败原因**。回退后重试会把结构化失败信息注入目标
   （`CodingCycle._retry_goal`），并明确告知改动已被回退，避免模型原样再撞一次。

后端可插拔（`backend/core/checkpoint.py`）：

| 后端 | 条件 | 能力 |
|---|---|---|
| `git` | 系统装了 git | 完整：diff / log / 分支 / 精确回退 |
| `snapshot` | 兜底，永远可用 | 文件级快照 + 文件清单，能回退，无 diff |

`CheckpointManager(prefer="git")` 自动择优，当前本机走 **git** 后端（实测 2.55.0）。
git 不可用时自动退化为 snapshot，回退能力不消失（但没有 diff）。
查询实际后端见 `GET /profile` 的 `checkpoint_backend`。

> 两处环境坑（已处理，见 `docs/CHANGELOG.md` §7）：
> 1. Git 安装后**已打开的进程 PATH 不会刷新**，故 `resolve_git()` 会在
>    PATH 之外回退到常见安装目录。
> 2. 仓库属主与当前用户不一致时，Git ≥ 2.35.2 会拒绝操作
>    （dubious ownership）。`_run_git` 统一加命令行级
>    `-c safe.directory=<cwd>` 放行，不污染用户全局 git config。

## 5. 验证示例

好的 `verify_command` 长这样（可运行、可断言）：

```python
import math_utils
assert math_utils.fib(10) == 55, math_utils.fib(10)
print("PASS")
```

不好的写法（流程会拒绝）：

- `"检查一下 fib 是否正确"` —— 自然语言，无法判定
- `""` —— 空命令
- `"print('done')"` —— 退出码恒为 0，不具备判别力（能过，但等于没验）

## 6. 对外接口

```
POST /encode
{
  "goal": "...",
  "verify_command": "import m\nassert m.f(1)==1\nprint('PASS')",   // 可选
  "max_attempts": 2
}
```

`ok: true` 仅代表**验证命令退出码为 0**，不代表模型自称完成。
旧的 `POST /run` 保留原行为（无强制校验、无检查点），便于对比。

## 7. 分层纪律：机制留在工作流，数字与策略进适配层

**这是本项目的核心架构约束。** 目标是标准工作流而非某个模型的定制产物，
因此模型必须可替换，且替换时不需要改工作流代码。

```
工作流层（模型无关，不得含任何模型特判）
  cycle / pipeline / checklist / checkpoint / memory
      ↓ 只依赖结构化协议与「能力契约」
适配层（可整体替换）
  model_profile.py   标准参数入口：标识 / 能力 / 预算 / 耦合
  llm.py             OpenAI 兼容客户端 + JSON 容错
      ↓
能力契约（启动自检）
  不满足 → 立刻显式报错，绝不静默劣化
```

### 7.1 标准参数入口

`backend/core/model_profile.py` 是**唯一**的参数入口，分四块：

| 块 | 作用 | 换模型时 |
|---|---|---|
| 标识 | `name` / `model` / `base_url` / `api_key` | 必改 |
| `ModelCapabilities` | 声明流程需要的能力 | 用于启动自检 |
| `ModelLimits` | 所有数字类预算 | 自动推导，可覆盖 |
| `ModelCoupling` | 该模型特有的补偿 | **可整体丢弃** |

`ModelLimits.from_context_window()` 让接入新模型只需要给一个上下文长度：

```
ctx<=8192   : rounds=15 steps=15 attempts=2   max_tokens=min(ctx/2,4096)
ctx<=32768  : rounds=20 steps=20 attempts=3   回灌截断=max(800,min(ctx/6,8000))
ctx>32768   : rounds=30 steps=25 attempts=3
```

> `max_tokens` 刻意在 8192 窗口时保持 4096——这是原先实测可用的值，
> 推导公式不允许在这一档上回退。需要更大生成预算请显式覆盖 `MAX_TOKENS`。

配置见 `.env.example`。`ORCH_*` 与 `WORKER_*` 可指向不同模型；
只配 `ORCH_*` 时 `WORKER_*` 自动继承。

### 7.2 耦合层的意义

`ModelCoupling` 收纳「为了让某个模型跑通而写的补丁」。它们**不属于工作流**：
工作流只负责调度与校验，不应该知道某个模型爱说「首先我」。

已迁入耦合层的项：

| 原位置 | 内容 | 性质 |
|---|---|---|
| `worker.py` `_PLAN_HINTS` | 计划句式识别（中文短语匹配） | 纯模型特判 → 移入 `coupling.plan_hints` |
| `worker.py` `ERROR_MARKERS` | 错误文本嗅探 | 改为只信结构化 `is_error_result`，文本嗅探降级为 `coupling.error_prefixes` |
| `llm.py` JSON 容错 | 去围栏 / 括号匹配 / 尾逗号 / 行注释 | 保留在适配层，由 `coupling.repair_json` 开关 |

**`DEFAULT_COUPLING` 是空实现**（不识别任何句式、不做文本嗅探），
即新模型默认不做任何补偿——这是正确的默认值。

### 7.3 启动自检

`ModelProfile.validate()` 在构建客户端时执行，`LLMClient.__init__` 会对
不满足的能力抛 `ModelCapabilityError`。`GET /profile` 可查看当前生效的
全部参数与校验结果。

**设计取向：宁可启动即报错，也不要静默劣化。** 静默劣化是换模型时最难查的故障——
表现为"它跑起来了，但一直在丢文件、空响应、悄悄产生假成功"。

## 8. 门禁 vs 建议：两类校验的边界

项目里有两套校验，**职责严格分开，不可互相替代**：

| | 门禁 CheckPipeline | 建议 `review_code` 工具 |
|---|---|---|
| 调度方 | **程序**，模型绕不过 | **模型**，自己决定调不调 |
| 决定成败 | 是（CHECK 未过不得进 VERIFY） | 否 |
| 检查内容 | 指定文件的语法 + lint | 任意代码的语法 + lint + 静态质量 |
| 结果去向 | 回退 / 重试 / 判 failed | 作为上下文回灌给模型 |

**为什么必须分开**：门禁若可被模型绕过就失去意义；而审查若变成门禁，
就会把"风格建议"升级成"成败判据"，导致大量本可通过的任务被判失败。

`review_code`（`backend/tools/quality.py`）覆盖的静态问题：

| 严重度 | 检查项 |
|---|---|
| high | 语法错误、裸 `except`、可变默认参数 |
| medium | 捕获 `Exception` 过宽、函数超过 50 行、嵌套深度超过 4、lint 问题 |
| low | 未使用导入、`import *`、缺返回注解、超长行 |

所有分析都是**确定性**的（AST + 已有 `check_syntax` / `run_lint`），
不引入任何需要模型参与判断的步骤——否则就又多一个幻觉源。
返回结构含 `issue_counts` / `metrics`（行数、函数数、最大嵌套、最长函数）。

## 10. 文件清单（manifest）：交付契约

### 10.1 解决的问题

此前验证阶段的文件清单只能从 `memory.artifacts` 里散落的 `write_file` 产物拼出来，
**文件压根没写就不在清单里**，验证自然不会去查它存在不存在。

L8 实测中：编排器声称产出了 3 个文件，实际 `contacts.py` 从未写出、
`cli.py` 的 `run()` 缺了 `args` 参数，而系统直到 `ModuleNotFoundError` 才发现
——那已经是很晚的间接症状。

### 10.2 分层：结构事实 / 设计意图

| | 结构事实（已实现） | 设计意图（后续） |
|---|---|---|
| 内容 | 有哪些文件、导出什么符号、签名、import 关系 | 为什么这样分层、模块职责、扩展点 |
| 来源 | **AST 扫描**，程序生成 | 模型编写 |
| 可信度 | 确定性强，可作判据 | 可能过时、可能是幻觉 |
| 模块 | `backend/core/symbol_index.py` | 待建 |

**关键纪律：结构部分不许模型改。** 若架构文档由模型自由编写，一旦代码与文档
不一致，模型会读着自己写的过时文档更加确信一切正常——L8 里
`storage.py` 把 agent 工具当普通函数调用（`def save(p,d): write_file(p,d)`）
就是这个问题的雏形：模型对自己的产出有一个错误的全局图景。

### 10.3 只报结构性事实

声明来自模型的计划，本质是自由文本。若拿它和代码做**语义**比对必然大量误报
（会像 L2/L3 那样白白耗尽重试），因此 violation 只包含程序能确证的：

| severity | kind | 含义 |
|---|---|---|
| error | `declared-missing` | 声明的文件不存在 |
| error | `symbol-missing` | 文件存在但缺了声明的符号 |
| error | `declared-broken` | 文件存在但无法解析 |
| warning | `dangling-import` | 本地模块间 import 了不存在的模块 |
| warning | `imports-missing-declared-module` | 导入了「本次声明要产出但不存在」的模块 |

**签名只作为信息列出，不参与判定**——计划通常只写符号名不写签名，硬比对会误报。

`declared` 为空时 `checked=False`，**不做判定**，避免把「模型没声明」误判成失败。

### 10.4 保守的导入检查

裸的顶层导入（如 `import numpy`）无法区分第三方库与本地模块，**一律不报**。
只报两类高置信度情况：相对导入无法解析、绝对导入的顶层是本地包但成员不存在。
宁可漏报也不误报——误报的代价是白烧重试次数。

### 10.5 接入位置

CHECK 阶段的**最前面**（早于语法检查）：如果该产出的文件压根不存在，
对它做语法检查没有意义，而且症状是间接的。现在会直接说
「计划要产出 X，但 X 不存在」。

`CycleReport.manifest` 记录完整对照，重试提示里会带上缺口明细。

## 11. 后期扩展：审查 / 架构跟踪角色（设计约束）

规划中的新角色：用**专用模型**做代码审查，以及架构跟踪与优化。
本项目的多角色基座已经就绪（`ModelProfile` 与角色解耦、`ORCH_*` / `WORKER_*`
独立配置、`ModelCoupling` 可按角色配），但下面四个约束必须先处理，
否则这个角色进来时会踩坑。**当前不实现，仅记录以免后期返工。**

### 11.1 角色 fallback 必须改为显式

`backend/core/config.py` 的 `resolve_profile(prefix, fallback)` 目前让未配置的
`WORKER` 继承 `ORCH`，这在两角色下是对的。但角色数超过两个后，
未配置的 `REVIEW` 会**静默继承编排器模型**——表现为"以为请了专业审查员，
实际还是同一个模型在审自己"，且不报错。

**要求**：角色数 > 2 时，把 fallback 换成显式角色表；未配置的角色要么
明确标记「未启用」，要么明确报错，不得静默顶上。

### 11.2 审查阶段在流程中的位置

`backend/core/cycle.py` 的 `PHASE_ORDER` 目前是硬编码线性序列
`(PLAN, WRITE, CHECK, VERIFY, RECORD)`，扩展时需明确插入位置：

| 位置 | 审查对象 | 取舍 |
|---|---|---|
| CHECK 后 / VERIFY 前 | 未验证的代码 | 可省一次验证，但审查意见混入大量"跑不起来"的噪音 |
| **VERIFY 后 / RECORD 前** | 已跑通的代码 | 审查对象可信；代价是功能已通过后仍可能返工 |

**推荐后者**：审查应针对「已经能跑通的代码」，否则意见质量会被
"根本跑不通"的噪音淹没。

### 11.3 最重要的约束：审查角色不得成为新的假失败源

§2.2 记录过一个缺陷：模型能改写调用方的验收标准。
如果审查角色获得否决权，等于换种形式重新引入同一问题：

> 门禁由程序判定 → 可信；门禁由模型判定 → 又变成"被考核方定义什么叫对"。

**要求**：

- 审查输出结构化的 `ReviewReport`，但**不得直接修改 `phase`**。
- 它影响的是**重试提示的内容**，不是成败判据。
- 若确实需要否决权，阈值必须来自**程序配置**
  （例如"仅 `blocking=True` 的问题触发返工"），不得由模型自由裁量。

与 `review_code` 的分工：确定性工具做**能算的**（语法/复杂度/裸 except），
模型角色做**要判断的**（抽象层次是否合理、职责划分是否清晰）。

### 11.4 架构跟踪是跨周期角色，依赖存储层

**代码审查（单文件 / 单 diff）与架构跟踪（跨 cycle）不是同一个角色。**
后者需要：积累 `CycleReport` 语料 → 跨周期对比 → 识别反复出现的问题模式。

现状不满足：`CycleReport` 只存在于单次运行的内存中，`data/sessions/*.json`
存的是原始任务记录，**从未为趋势分析组织过**。

**要求**：该角色依赖「结构化上下文压缩 + 存储抽象」。若它在路线图上靠前，
存储层的优先级需要前移，否则这个角色没有原料可用。

## 12. 能力边界实测（2026-09-25）

模型 qwen2.5:7b，8 级难度阶梯，通过率 **2/8**（详见 `能力评估报告.md`）。

| 级别 | 任务 | 结果 |
|---|---|---|
| L1 | 单文件 / 单函数 | ✅ |
| L2 | 单文件 / 控制流 + 边界 | ❌ |
| L3 | 单文件 / 递归 + 输入校验 | ❌ |
| L4 | 单文件 / 类 + 异常语义 | ✅ |
| L5 | 多文件 / 跨模块 + 算法 | ❌ |
| L6 | 单文件 / 文本解析 + 聚合 | ❌ |
| L7 | 单文件 / 文件 IO + JSON | ❌ |
| L8 | 多文件 / 大程序 | ❌ |

失败分两类，**不要混淆**：

- **模型能力类**（L2/L3/L6）：规格已写清，模型仍按直觉实现。
  换更强模型即可，不适合在工作流里打补丁。
- **架构缺口类**（L5/L7/L8）：系统没有「本轮该产出哪些文件」的显式模型，
  验证只能从散落的 `write_file` 产物拼清单——**文件压根没写就不在清单里**。
  这是 §8 的 manifest 要解决的，属通用机制。

> 测试前提：修掉「模型可改写调用方 verify」的缺陷后数据才可信（见 §2.2）。
> 修复前 L3 之所以显示通过，是模型把断言改成了 `isinstance(factorial(-1), ValueError)`
> ——一个永远不可能成立的断言。

**重要正面结论**：门禁与回退完全正常。6 次失败全部判为
`phase=failed` + `rolled_back=True`，**没有一次把错误结果当成功交付**。

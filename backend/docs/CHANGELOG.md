## 1. `fetch_url` 内网拦截失效（安全项）—— ✅ 已修复

**发现**：`tools/net.py` 中

```python
try:
    ip = ipaddress.ip_address(host)
    if ip.is_private or ip.is_loopback or ...:
        raise ValueError("禁止访问内网地址")   # ← 这个 raise
except ValueError:
    pass                                       # ← 被这里吞掉
```

`ipaddress` 对**域名**抛 `ValueError`（正常），但**私有 IP** 也抛 `ValueError`。
两者共用一个 `except`，导致安全判断被自己的异常处理吞掉。

**实测（修复前）**：`127.0.0.1` / `10.0.0.5` / `169.254.169.254` 全部 **ALLOWED**，
只有 `localhost` 靠另一行的显式判断侥幸拦住。

**修复**：`try` 只包住 `ipaddress.ip_address(host)` 这一步，把「不是 IP 字面量」
与「是私有 IP」两种 `ValueError` 分开处理。同时补齐 `.localhost` 后缀、
末尾点号、`0.0.0.0`、IPv6 回环/link-local、组播等情形。

**验证**：`python tests/unit/test_net_guard.py` —— 20 个用例全过，含 6 项关键回归。

**残余风险（未修）**：DNS rebinding / TOCTOU——域名在校验时解析为公网、
请求时被重新解析到内网，本层拦不住。彻底防护需在传输层做 peer-IP 校验。
**暴露到公网前必须补上。**

## 2. `PHASE_ORDER` 定义了但零消费方 —— ✅ 已修复

**发现**：`core/cycle.py` 定义 `PHASE_ORDER` 并注释「CHECK 未通过时不允许进入
VERIFY」，但全仓库唯一引用就是定义处。实际阶段推进是 `CodingCycle.run` 里
硬编码的——**注释宣称的约束不由它保证，改这个常量不会生效**。

声明了却不兑现的约束，比不写更危险。

**修复**：`CycleReport.enter()` 现在调用 `is_valid_transition()`：
- 除 `FAILED` 外，阶段必须沿 `PHASE_ORDER` **恰好前进一步**，不得跳跃或倒退
- `FAILED` 可从任意阶段进入，之后只能重新回到 `PLAN`
- 已在 `PLAN` 时重复进入 `PLAN` 视为重启本轮（多次重试会走到这里）
- 非法推直抛 `ValueError`，带明确的合法顺序提示

顺带修正了 `CodingCycle.run` 的阶段顺序：manifest 阻塞时原先会
`PLAN → CHECK` 跳级，现在统一为 `PLAN → WRITE → (manifest) → CHECK`。

**验证**：`python tests/unit/test_phase_order.py` —— 8 项全过，
含「越级被拦」「跳过 CHECK 被拦」「倒退被拦」「多次重试不误报」。

## 7. git 回退后端未真正接管 —— ✅ 已修复

**发现**：系统装了 git（2.55.0），但 `CheckpointManager` 仍选中 `snapshot`。
排查出**两个独立原因**：

**(a) 进程 PATH 未刷新。** Git 安装只更新注册表，已打开的终端/进程看不到
`C:\Program Files\Git\cmd`，于是 `shutil.which("git")` 返回 None。
`_run_git` 捕获 `FileNotFoundError` 后静默降级，界面上看不出任何异常。

**修复**：新增 `resolve_git()`，按「PATH → 常见安装目录」顺序定位并缓存结果；
POSIX 与 Windows 路径都覆盖。`/profile` 的 `checkpoint_backend.git` 会显示
`executable` / `from_path` / `note`，明确告知是否走了回退路径。

**(b) Git 的 dubious ownership 防护。** 仓库属主与当前进程用户不一致时，
Git ≥ 2.35.2（CVE-2022-24765 的修复）会**拒绝所有操作**：

```
fatal: detected dubious ownership in repository at '.../workspace'
```

**修复**：`_run_git` 统一加命令行级 `-c safe.directory=<cwd>`。
选它而不是 `git config --global --add safe.directory`，是因为后者会**污染用户全局
配置**；命令行级只影响本次调用。

**附带修复**：`commit()` / `_has_changes()` 原先吞掉 git 的 stderr 直接返回
`None`/`False`，导致回退机制「看起来启用了其实没工作」。现在失败时打印 stderr。
`commit()` 还补上了「仓库尚无任何提交」时用 `--allow-empty` 建初始提交。

**验证**：`python tests/unit/test_git_backend.py` —— 11 项全过，含
真实提交历史、回退后 HEAD 与工作区状态、`_tmp/_debug` 未被追踪、无改动提交幂等。

**端到端**：`python tests/bench/run_levels.py 1 1` 返回真实 SHA，
`workspace` 里可读到 `[cycle …] baseline` 与 `[cycle …] 创建 add.py` 两条提交。

> ⚠️ 测试里**不要裸调 git**。Git 的 ownership 防护会让裸调用失败，
> 而 backend 已放行——裸调会得到与真实行为不符的假失败。
> 请复用 `core.checkpoint._run_git`。

## 9. 新增存储层与结构化压缩 —— ✅ 已落地

**目标**：为「上下文压缩」「架构跟踪角色」提供原料，同时避免把压缩交给模型
自由生成（那会新增幻觉源，并把错误固化）。

**新增文件**：

| 文件 | 职责 |
|---|---|
| `storage/store.py` | `Storage` Protocol + `FileStorage`（JSONL 事件 + JSON 快照） |
| `core/compress.py` | `reduce_cycle` / `reduce_all` / `cross_cycle_failures` |

**核心纪律（写在 `core/compress.py` 模块 docstring 里）**：

> 压缩的输入只能是被程序校验过的结果，不能是模型的自由摘要。

每个事实带 `source`（可回溯到哪条事件）与 `confidence`：

| confidence | 来源 | 能否作判据 |
|---|---|---|
| `verified` | verify 退出码 / manifest 文件与符号实测 / syntax / lint | 能 |
| `declared` | 计划声明（意图，不是现实） | 否 |
| `assumed` | 模型自述（任务 output 摘要） | **绝不能** |

未登记的来源一律兜底为 `assumed`——**安全默认**。

**可替换性已验证**：测试里用一个 `MemoryStorage` 替换文件实现，
`isinstance(ms, Storage)` 成立，且两种实现产出的压缩结果**逐字段一致**
（证明压缩与存储形态无关，将来接数据库只需换实现）。

**存储是旁路**：`CodingCycle._emit` 内兜住所有异常——存储写失败**绝不能**
让 cycle 失败。

## 10. 远程人工决策 —— ✅ 已落地

**需求**：决策流不必一直盯着，可以从手机输入决策并继续。

### 先说的实话：QQ/微信走不通

| 通道 | 双向 bot 能力 | 结论 |
|---|---|---|
| 个人微信 | 官方**无** API；第三方方案基于逆向/hook，**违反用户协议**、封号风险高 | ❌ |
| 个人 QQ | 官方 bot 平台需企业/组织资质审核 | ❌ |
| 企业微信 | 有正规 API，但需企业/组织才能注册 | ⚠️ |
| **钉钉** | 群自定义机器人 webhook，**个人可用、免费** | ✅ 唯一能正规落地 |

### 绕开限制：推送通知 + 链接跳转审批

交互式审批放在**网页**里，IM 只负责「发一条带链接的消息」：

```
验证连续失败 2 次
  → 钉钉推送：「⚠ 需要你决策… [👉 点击查看并决策]」
  → 手机点开审批页（渲染结构化上下文 + 按钮）
  → 点「再试一次」→ 决策写入队列 → cycle 继续
```

好处是**不绑定任何平台**：新平台只需实现 `core/notify.py` 的一个 `Notifier`。
审批页还能直接渲染已有的结构化快照（计划声明 / 验证失败细节 / 清单问题），
这是聊天消息做不到的。

### 分层

| 层 | 文件 | 职责 |
|---|---|---|
| 决策层 | `core/decisions.py` | 与通道无关：数据模型、状态机、持久化、超时策略 |
| 投递层 | `core/notify.py` | 可插拔：Console / DingTalk / Webhook(企业微信·Slack) |
| 审批页 | `web/decisions.py` | 手机端交互（无外部依赖，离线可用） |

### 决策点只设两处

| 位置 | 触发 | 为什么值得停 |
|---|---|---|
| `repeated_failure` | 验证连续失败达阈值 | 「模型能力不够」的信号，需要人拍板 |
| `risky_rollback` | 回退会覆盖已有文件前 | 回退会丢改动，属有风险动作 |

**程序能判定的确定性事实（清单缺失、语法错误）不会打扰你**——那是客观事实，
不该占用人的注意力。

### 超时 fail-safe

| 决策类型 | 超时默认 | 理由 |
|---|---|---|
| `risky_rollback` | `abort` | 不覆盖已有文件 |
| `repeated_failure` | `stop` | 停止而不是空转烧预算 |

### 关键设计：跨进程作答

`_wait_for_answer` 用**文件轮询**而非内存 `Future`，使
「CLI 跑 cycle + Web 服务接收作答」两个进程能协作成立。
**推送失败时不等待**——推不出去就没人会作答，等待只会挂死。

### 验证

| 测试 | 项数 | 覆盖 |
|---|---|---|
| `tests/unit/test_decisions.py` | 30 | 生命周期、非法作答拦截、超时 fail-safe、通道退化、**跨实例作答→恢复** |
| `tests/unit/test_approval_web.py` | 23 | 页面渲染、结构化上下文、按钮、非法选项 400、404、令牌 403/200 |

最关键一项：后台线程用**另一个 `DecisionManager` 实例**作答，
主线程阻塞等待后正确恢复并采用人的选择（实测等待 2.0s）。

### 安全

- 默认无鉴权，适合局域网自用；设 `AGENT_APPROVAL_TOKEN` 后接口要求 `?t=<token>`
- webhook 与 token 只从环境变量读，**已加入 `.gitignore`**（`storage_data/`、`.env`）
- 作答只接受选项列表内的值，防止前端被绕过时注入任意动作

### 已知限制

- **手机需能访问审批页**。局域网内可直接用；出门在外需内网穿透（cloudflared/ngrok）
- **`on_decision=wait` 会阻塞一个请求线程**。个人自用可接受；要做成生产级

- 钉钉通道**只验证了加签 URL 生成与载荷构造，未实测真实推送**（无真实 webhook）

## 11. 反思分析器（自我反思的第一步）—— ✅ 已落地

**需求**：让 agent 具备"自我反思、分析问题"的能力，代替人的一部分职责
（发现反复出现的问题、建议改什么）。

### 为什么先做"程序统计版"

反思的质量上限由**原料**决定。若让模型"回顾刚才发生了什么"，它会基于
**自己的记忆**反思——而模型对自身行为的记忆极不可靠。本项目实测：
模型声称建了 3 个文件，实际只建了 1 个（L8）。

所以第一版**完全不用模型**：从事件流与 `Snapshot` 做统计，产出结构化模式 + 证据。

### 核心纪律：只用 verified 事实

每个检测器**只读程序校验过的结果**（verify / syntax / lint / manifest / rollback）。
模型自述（`confidence=assumed`）唯一被引用的地方是 `detect_false_claims`，
且只用于**指出矛盾**。这是从构造上杜绝幻觉，而不是靠提示词约束。

### 六个检测器

| 检测器 | 发现什么 | 置信度 |
|---|---|---|
| `repeated_failure` | 同一 `reason_hash` 跨 cycle 反复出现 → 系统性 | high（≥3 cycle） |
| `false_claim` | **模型声称成功但验证未通过** | high |
| `failure_cluster` | 失败集中在同一文件 | medium |
| `retry_hotspot` | 尝试次数高仍未通过 | medium |
| `manifest_gap` | 交付清单缺口重复出现 | medium |
| `budget_exhaustion` | 命中轮次/步数上限 | medium |

### 边界（刻意设计）

- **只产出建议，绝不自动应用**。「建议」与「执行修改」分离是关键：
  一个会自己改自己 prompt 的 agent，最大风险不是改坏，而是**改得看不出好坏**。
- **不参与成败判定**：不影响 `phase`，只影响人（或下一次规划）看到什么。
- 每条模式**必须带证据**，指向具体事件（`cycle#seq`）。解析不出位置时只显示
  cycle —— **不渲染成 `#0`**，那看起来像精确位置，实际是编的。

## 12. 技能：稳定流程封装成固定调用链路 —— ✅ 已落地

**需求**：某类代码生成流程已经稳定，把它打包成固定调用链路，不必每次让模型重新规划。

### 核心洞察：技能就是「预先烘焙的计划」

`CodingCycle.run()` 只要求 orchestrator 有 `run(goal)` 并返回 `OrchestratorResult`。
所以固定链路**不需要新增旁路**——实现同一个接口（`SkillRunner`），
就能复用全部既有机制：manifest 校验、语法/lint 门禁、验证回流、回退、
事件存储、人工决策。

这比另写一条执行路径安全得多：**功能不会因为走"快捷通道"而绕过门禁**。

```
普通流程：模型 PLAN（1 次 LLM） → 模型执行（N 次 LLM）
技能重放：读技能（0 次 LLM）   → 模型执行（N 次 LLM）
```

省掉的是**规划那一步**，不是执行。执行仍由模型按参数生成代码，因此仍需实测。

### 数据结构

| 层 | 作用 |
|---|---|
| `SkillParameter` | 变化的部分（函数名、文件名…） |
| `SkillFile` | 产出契约：路径模板 + 必须有符号 |
| `Skill` | 整条链路：文件 + 验证模板 + 参数 + 参考实现 |
| `SkillStore` | 落盘、检索、使用统计 |

占位符 `{name}` 可出现在**目标、文件路径、符号名、验证命令**里；
`validate()` 会拦住"用了未声明的参数"这类坏定义。

### 三条纪律

1. **只有验证通过的 cycle 才能被提升** —— `promote_from_report()` 强制检查
   `phase == "record"` + verify 通过 + 有声明清单。未验证的流程不是"稳定流程"，
   封装它等于**批量复制不确定性**。
2. **重放仍过全部门禁** —— 技能记录的是"曾经成功过"，不是"永远正确"。
   实测：少写文件 → 判失败；验证不过 → 判失败。
3. **参考实现不作为直接复制产物** —— 任务说明里明确写"参数已变化，不要照抄"。

### 技能是资产，不是遥测

默认落在 `storage_data/skills/`，但性质与其它 `storage_data/` 内容不同：
其它是运行遥测（可随时删），技能**需要备份与版本管理**。

因此 `.gitignore` 对它做了例外。这里踩了个坑：
**`!storage_data/skills/` 单独写不生效**（父目录被排除后 git 不会进入它），
而 `!storage_data/` 又会把 snapshots 一并放进来。正确写法是三步：

```gitignore
!storage_data/          # 先重新包含父目录
storage_data/*          # 再排除其余内容
!storage_data/skills/   # 最后放行技能目录
```

已加验证：技能入库、`snapshots/` 与 `events.jsonl` 仍被忽略、`.env` 仍被挡住。

### 对外接口

| 入口 | 用途 |
|---|---|
| `GET /skills` | 列出技能（含 uses/successes 成功率、problems 校验结果） |
| `POST /skills/{id}/replay` | 按固定链路重放，**仍走完整门禁**，结束后回写统计 |
| `core.skills.promote_from_report()` | 从成功 cycle 提升（带闸门） |
| `core.skill_runner.SkillRunner` | 作为 Orchestrator 的替代实现 |

### 验证

`tests/unit/test_skills.py` **46/46**：

- 技能定义校验（未声明参数 / 缺 verify / 无产出文件 / 缺必填参数，全部拦截）
- 模板渲染（路径、符号、验证命令；未知占位符保留原样）
- **与 CodingCycle 集成**：正向通过全部门禁；少写文件被判失败；验证不过被判失败
- 提升闸门：未通过 / verify 失败 / 无清单 / 缺参数声明，四种情况全部拒绝
- 参考实现 `example` **从磁盘读取**（worker 的 file artifact 只存路径不存内容）
- 使用统计回写（`describe()` 显示成功率）

### 尚未做

  要做需对比多次成功运行、diff 出变化点。

## 13. 封装优化角色：形态指纹 + 参数识别 + 审核闸门 + 副本机制 —— ✅ 已落地

**需求**："自动参数识别考虑从外部加个角色，专门封装优化的"；
"可以先建立副本，不影响元项目"；"要加个审核机制，怎么算可封装复用"。

### 它是离线分析器，不是运行时角色

| | 运行时角色（编排器/执行器/审查员） | 本角色 |
|---|---|---|
| 作用于 | **活着的 cycle** | **已完成的历史** |
| 输出 | 影响当前执行 | 产出可复用资产 |
| 风险 | 可能污染流程 | 只读历史，**天然安全** |

"先建副本"这条原则正好落在这里：它**不碰运行中的流程**，
只读 `storage_data`、只写候选与副本区。

### 四层结构

| 层 | 文件 | 职责 |
|---|---|---|
| 形态指纹 | `core/shape.py` | 判断两次运行是否「同一类任务」 |
| 候选分析 | `core/package.py` | 变化点识别 + 打分 |
| 审核与副本 | `core/promote.py` | 程序判据审核 + 隔离安装 |
| 落点 | `storage_data/skill_candidates/`、`skill_staging/` | 候选区 / 副本区（与正式库分开） |

### 关键难点：单次运行识别不出参数

"哪些部分是变量"只有对比**多次同类运行**才知道。单次运行看起来一切固定——
那正是过拟合的来源。所以必须先分组（形态指纹）再 diff（变化点）。

### 形态指纹踩了两次坑（值得记）

指纹的松弛程度极其难调，我改了三次才对：

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 | 抹标识符 + 抹数字 | `fib(10)==55` 与 `factorial(5)==120` 骨架相同 ✓，但**没处理 `[3,1,2]`**，同类因方括号被拆开 ✗ |
| v2 | 只抹标识符、**保留字面量** | 结构区分度上来了，但 `fib(10)==55` 与 `factorial(5)==120` 又分到不同组 ✗ |
| v3 | 标识符→`ID`，字面量→`<int>`/`<str>` | 两者都对 ✓ |

**结论：结构签名要对具体值不敏感，参数提取才用具体值。两级分工。**
另外 v3 顺带修正了一个隐蔽 bug：子串替换会把 `import fib` 与
`assert fib.fib(...)` 里的 `fib` 变成 `{p1}.{p1}`（实为两个不同变量），
改成**词法级重建**后消失。

### 审核闸门是程序判据

| 检查 | 拦截什么 |
|---|---|
| 证据量 ≥ 2 次成功 | 单次运行的过拟合 |
| 分数 ≥ 0.7 | 证据不足（**2 次成功不足以过关**——区分不出"固定形态"与"碰巧相似"） |
| 验证模板完整 | 缺了就无法判定重放成败 |
| 识别出 ≥1 个变量 | 常量流程谈不上复用 |
| 参数已命名 | 自动名 `p1` 没有语义，不能入库 |
| 参数名不重复 | |
| 转成的技能定义自洽 | 残留未替换占位符等 |
| ID 不与正式库冲突 | |

`auto_rename_map()` 按 kind 给出**弱语义建议**（path→filename、symbol→func、
字面量→expected_int），但明确标注"命名可能不准，需人工确认"——
自动命名在一般情形下不可解，本模块不假装能猜对。

### 副本机制（落实"不影响主项目"）

```
候选 --审核闸门--> 副本区 --重放实测--> 正式库
                       └─ 失败则丢弃，正式库不受影响
```

`promote_staging_to_live(proven=...)` 的 `proven` **必须来自真实重放结果**，
不能凭审核分数推断——审核只能筛掉明显不合格的，**不能证明它能跑通**。

### 真实数据验证（暴露了一个典型形态）

对历史运行分析后产出 3 个候选，其中：

```
变量: []
理由: 证据充分：4 次成功运行
      未识别出变量：可能是常量流程，复用价值有限
```

**这是过拟合的教科书形态**：之前测试反复用同一个目标（`实现 add`），
路径/符号/验证命令零变化。审核闸门会拦住它（`识别出至少一个变量` 失败）——
这正说明闸门在起作用，而不是形同虚设。

### 对外接口

| 入口 | 用途 |
|---|---|
| `GET /candidates?analyze_now=1` | 列出候选（含分数、变量、弱语义建议名）。**只读** |
| `POST /candidates/{id}/install` | 审核并装进**副本区**；未过审返回 400 并列出拦截点 |
| `POST /candidates/{id}/promote` | 副本提升到正式库（需 `proven=true`） |

### 验证

`tests/unit/test_package.py` **42/42**：

- 形态指纹：同类归组、异类分开、失败的不参与、列表入参与标量入参分开
- 变化点识别：抽出外壳、多变化段不硬凑、单元素拒绝归纳
- 打分：证据越多分越高、缺模板显著扣分、2 次不达阈值 / 3 次达阈值
- 审核闸门：未命名 / 重名 / ID 冲突 / 单次运行，全部拦截
- **副本机制**：审核通过只进副本、未实测不许提升、实测后提升、丢弃不影响正式库

### 尚未做

- **跨 session 分析**：目前只读本地 `storage_data`
- **技能失效检测**：代码演进后旧技能可能过时
- **自动命名**：目前只给弱语义建议，仍需人工确认（这点是刻意的）

正例（修正后）：陈述**当前选择行为**——
"git 可用时选用 git，不可用退化为 snapshot；查实际后端见 `/profile`"。
这样无论环境怎么变，描述都成立。

同样地，`MODULES §19` 与 `OPERATIONS §9` 的清单**只列当前仍存在的**，
已修的直接删掉，不留"✅ 已修复"墓碑。

### 15.3 机制修正：把一致性变成可执行检查

新增 `tests/unit/test_doc_consistency.py`（**33 项**），把"可机械验证的一致性"
变成测试。它覆盖六类高频漂移：

| 检查 | 抓什么 |
|---|---|
| 工具数量/分组 | 文档写的数字 == `len(TOOLS_MAP)` 与实际 profile 分组 |
| 工具清单覆盖 | `MODULES §17` 必须列出全部工具名 |
| 已删除符号 | 上游文档不得把 `debug_head_chars` 等**当现有字段**引用（说明"已删除"的提及允许） |
| 过时措辞 | 黑名单短语（`未安装 git` / `不会自动加载` / `是文档性常量` …） |
| § 交叉引用 | 每个 `§X.Y` 必须在**全部文档的标题**里有对应（引用可跨文档） |
| 未修清单 | 条目标题里不得有"已修复"墓碑；引用的项目路径必须存在 |
| **版本戳** | 各上游文档声明的 `同步至 CHANGELOG §N` == CHANGELOG 最新条目号 |

**版本戳**是评审建议的最后一条，采纳了：四份上游文档 + `CYCLE.md` 顶部都标了
`> 同步至 CHANGELOG §14`。下次改动不同步时，这个数字会立刻暴露。

> 写这个检查器时也踩了它自己的坑，都已修：
> ① 正则漏了字母子编号（`4.0` / `7.1.1`）；
> ② 把代码块里的 `# 注释` 当成标题；
> ③ 误以为 `§X` 只能引用同文档章节 —— 实际可跨文档（`CYCLE.md` §9.2）。
> 这些误报本身说明：**检查器也要能被信任，否则它只会制造噪音。**

### 15.4 这一批处理后仍未解决的

- **语义漂移**检查不了：检查器只能抓机械可验证的部分
  （数量、符号、措辞、引用、版本戳）。描述与实现"意思不一致"仍需人工审。
- **版本戳需要人记得改**：现在它能**暴露**未同步，但不能自动同步。

## 16. 文档审查纳入 agent 能力范围 —— ✅ 已落地

**需求**："我的 agent 也要把文档审查纳入范围"。

### 16.1 先分清两个层次（这决定谁来审）

| 层次 | 例子 | 谁能判 |
|---|---|---|
| **机械一致性** | 工具数是 16 还是 18；`§9.2` 是否存在；符号是否已被删除 | **程序**——可验证，**可作门禁** |
| **语义准确性** | "这段关于分层的描述是否成立"；"这个解释是否误导" | **模型**——只能建议，**不能裁决** |

这与 `CYCLE.md` §8「门禁 vs 建议」是同一条纪律，也承接 §2.2：
**验收标准不能由被考核方定义**。所以文档审查也分层落地——
机械层进测试与工具，语义层留作后续的审查角色（建议性）。

### 16.2 一个必须先解决的集成障碍：子循环读不到文档

实测确认：

```
read_file("docs/MODULES.md")   -> 被映射到 workspace/docs/MODULES.md（不存在）
read_file("../docs/MODULES.md") -> 被路径防护拒绝
```

`tools/files.py` 把访问限制在 `workspace/`——那是**代码生成沙箱**，边界是对的。
**不该为了审文档而放宽它。**

解法是**另开一扇只读窗**（`core/doc_access.py`）：

| 约束 | 做法 |
|---|---|
| 只读 | 只提供 `read()`，**没有写路径** |
| 显式白名单 | 默认 `README.md` / `CYCLE.md` / `docs`，可用 `DOC_REVIEW_ROOTS` 覆盖 |
| 拒绝穿越 | 绝对路径、盘符、任何 `..` 一律拒绝 |
| 大小上限 | 256 KB，**超限直接拒绝而非静默截断**（截断会让审查漏内容） |

### 16.3 检查逻辑只写一份

`core/doc_review.py` 是**共享判据**：`tests/unit/test_doc_review.py` 与
模型可调用的工具**调同一套代码**。若各写一份，两处必然分叉——
那正是本项目一直在治理的漂移。

五项机械检查：代码块语法、`import` 引用、`模块.符号` 引用、
§ 交叉引用、`/profile` 字段名。

### 16.4 新工具 `review_document`（第 18 个）

| 能力 | 说明 |
|---|---|
| 列表模式 | 不传 `path` 时列出可审查的文档 |
| 审查模式 | 传 `path` 返回 `{passed, checks, failures}`，每条带**证据**（行号/符号） |
| 定位 | **建议性**，不参与 cycle 成败判定；但机械部分结论可信 |

实测能精确抓到三类问题（用故意写坏的文档验证）：

```
[NG] python 代码块语法合法   ↳ L3: invalid syntax
[NG] import 指向真实符号     ↳ core.config.this_symbol_does_not_exist
[NG] 「模块.符号」引用存在    ↳ core.config.also_missing
                              ↳ tools.registry.nope_nope
```

### 16.5 检查器缺口：这次是被自己抓到的

加完 `review_document` 后，`test_doc_consistency.py` **立刻报错**：

```
FAIL  README.md: 写了「17 个工具」，实际 18
FAIL  MODULES 未列出的工具: ['review_document']
FAIL  coding: 文档写 14，实际 15
```

这正是上一轮建它的目的——**不用靠人记得同步**。

但它也暴露了自己的缺口：只抓"数字"，没抓"结构声明"。
于是补了两项：

- README 项目结构里声明的路径必须存在
- **真实存在的顶层包必须在 README 结构里出现**

补完立刻抓到 README **漏了 `web/`**（手机端审批页所在目录）。

## 17. 多模态接口预留 + 上下文预算管理 —— ✅ 已落地

两项改动：一项是你要求的**多模态预留**，一项是我分析里挂着的**最高杠杆优化**。

### 17.1 多模态：新增 `vision` 角色

**为什么是独立角色而不是给 worker 加能力**：图像模型与代码模型通常不是同一个，
且不该强制 worker 必须支持图像。这也顺带检验了角色表设计是否真的可扩展——
`vision` 的接入**没有改一行已有角色逻辑**，只是登记一条：

```python
"vision": RoleSpec(
    key="VISION", name="vision",
    purpose="图像理解（截图/图表/设计稿 → 结构化描述）",
    # 无 inherits_from、无 has_builtin_default → 未配置即"未启用"
),
```

`ModelCapabilities` 新增三项：`supports_image_input` / `max_images_per_request` /
`supports_image_detail`。`validate()` 对 `vision` 角色额外校验图像能力。

### 17.2 核心纪律：**能力不满足时显式失败，不静默丢图**

静默丢图比报错更糟——模型会凭文本臆测，产出一个**看起来有依据的幻觉答案**。
所以未声明视觉能力时直接抛 `VisionError`，并在消息里给出修复方式。

同理 `detail` 字段（OpenAI 扩展，非通用）：**只在模型显式声明支持时才下发**。
未声明的实现收到它会直接报错，那属于"自己制造故障"。

### 17.3 只读白名单：防读任意文件

本地图片走白名单目录（与 `doc_access` 同一思路）：
默认 `assets` / `workspace`，可用 `VISION_IMAGE_ROOTS` 覆盖；
绝对路径、盘符、任何 `..` 一律拒绝；单图 8MB 上限；类型按扩展名校验。

`build_vision_message()` 把三种来源（本地路径 / http 直链 / data URI）
统一成 OpenAI 兼容的 content 数组，label 作为独立文本块附带。

### 17.4 上下文预算管理（原"按条数截断"的修复）

`summary_for_orchestrator` 有两个真问题，这轮一并修掉：

| 问题 | 旧行为 | 新行为 |
|---|---|---|
| **验证结论在最后** | 放 prompt 末尾；一旦被截断，**最该看到的信息先丢** | 放**最前面**，且优先级 0 永不省略 |
| **按条数硬截断** | 取"最近 12 条"，更早记录**静默消失** | 按**优先级 + 字符预算**填充，截断时**明说丢了多少** |

优先级顺序：`验证结论 > 失败任务 > 关键事实 > 已有产物 > 已完成任务`。
已完成任务**按时间倒序填充**，保证"最近发生的事"一定在预算内。

预算来自 `ModelLimits.orchestrator_prompt_chars`（`max(2000, min(cw//6, 24000))`），
由 `context_window` 推导——**预算仍然只有一个来源**。

两处省略提示都会出现：

```
…（省略较早的 28 条记录）                       # 进了该段但没填满
…（因 prompt 预算不足，省略了 33 条任务记录）      # 预算在到达该段前就耗尽
```

第二条是补的兜底：否则"一条记录都没进来"时又变成静默截断。

### 18.1 版本备份机制（`tests/backup.py`）

3. 把本次备份写进 `docs/VERSIONS.md`（详细记录：改了什么、验证结果、回退命令）

## 19. 压缩快照回流进编排器 prompt + 待确认清单 —— ✅ 已落地

两件事：把 §17 之后一直"就绪但未接线"的压缩快照真正接进主循环，
以及把**只有项目所有者能定**的事项集中成一份可拍板的清单。

### 19.1 快照回流：`CodingCycle` → `Orchestrator` → `SharedMemory`

**为什么之前接不上**：`SharedMemory` 由主循环在 `Orchestrator.run()` 内部新建，
属于"每轮新建、逐轮累积"；而压缩快照需要**事件流 + cycle_id**，
只有 `CodingCycle` 同时握着这两样。两者生命周期不同，硬接会产生构造顺序上的循环依赖。

**解法（三段式，依赖方向单一）**：

| 层 | 做什么 | 不做什么 |
|---|---|---|
| `CodingCycle._structured_context()` | 从事件流算快照，渲染成**字符串** | 不碰 prompt 排版 |
| `Orchestrator.context_provider` | **每轮决策前**调用一次，写入 memory | 不解析、不判断内容 |
| `SharedMemory.set_structured_context()` | 存字符串，在渲染时按预算排版 | 不依赖 `compress` |

`SharedMemory` 只存**渲染结果**而不是 `Snapshot` 对象 —— 这样 `core/memory.py`
不必 import `core/compress.py`，压缩与排版各自可独立测试。

**每轮决策前刷新而不是 run() 开头刷新**：同一 attempt 内主循环可能决策多轮，
每轮都该看到"到此刻为止"的实测事实。附带的好处是同一 cycle 的各次 attempt
共享 `cycle_id`，所以第 2 次 attempt 能看到第 1 次的 syntax / lint / manifest / verify
**实测结论**（带 `verified` 标注），而不只是 `_retry_goal()` 里那句自然语言。

**渲染位置**：`【验证结论】→ 目标 → 【结构化上下文】→ 失败任务 → 关键事实 → 产物 → 已完成`。
放这个位置的理由：它比"模型自述"可信（全部来自程序实测），
但**绝不能挤掉验证结论**——所以给它的是**独立预算上限** `max(200, min(budget//3, 1500))`，
超出时写"…（结构化上下文超出预算，已截断）"，不静默丢。

**旁路纪律**：取快照的任何环节（读事件、压缩、渲染、provider 本身）抛异常
一律降级为"无结构化上下文"，只打印一行日志，**绝不影响主循环**。
它是增强，不是判据。

**跨轮反复失败**也一并注入：`cross_cycle_failures(min_count=2)` 找同一 `reason_hash`
在多轮里重复出现的模式（系统性问题），渲染为「跨轮反复失败（先修根因）」。

### 19.2 `expected_output` 接线：只作 declared 事实，不作门禁

`Task.expected_output` 此前"定义了但没人用"。现在它进入 `plan` 事件的 `intent` 列表，
被压缩成 `confidence=declared` 的事实，渲染在「计划声明（尚未确认为现实）」段。

**为什么不做成门禁**：它是**自由文本**（"可运行的 app.py"），
要做成门禁就必须让模型判断"是否达成"——那就等于把幻觉源接进判据链。
纪律是"门禁判据必须能机器判定"，所以它只能作可回溯的声明。

### 19.3 顺带修掉的文档漂移（`CYCLE.md §9`）

`CYCLE.md §9` 标题是"尚未完成"，里面却混着两条**早就落地**的能力
（架构视图工具、结构化上下文压缩），还写着"工具补 `risk`/`visible_to`/`stage`"
而实际上 `profiles` 过滤已经落地。已重写该节：只列**当前仍缺**的
（工具 `risk`/`stage`、`expected_output` 门禁、存储抽象、设计注记层），
把已落地能力的**设计理由**移到新增的 §9.1 —— 理由值得留，但不能再标"尚未完成"。

同理，`docs/CHANGELOG.md §10` 的"尚未修复"表加了修复标注
（`已修，见 §19` / `部分修复` / `仍未修`）：不改写历史，也不让人误读成"现在还是坏的"。

### 19.4 待确认清单（`docs/PENDING_DECISIONS.md`）

## 21. 上游→前端兼容契约（`core/contract.py`）—— ✅ 已落地

**起因**：前端给了标定文档（SPEC.md），里面写明它的做法是**扫上游取事实**——
阶段、事件词表、工具、运行报告四处全在上游。这意味着上游**每次改动都在改契约**。

**为什么这是个问题**：前端按纪律"认不出就降级显示"，
所以上游删一个事件、改一个 payload 键**不会让前端报错**，只会让它**静默少显示**。
`dead_calibrations` 只在人为打开 `/api/spec` 时才看得见。
这正是 SPEC §1 里"两边各手写一份"的老问题换了个方向：以前是前端写死，现在是前端静默漏。

### 21.1 做法：声明 + 自扫描

| 部分 | 内容 |
|---|---|
| **声明** | `EVENTS`（12 种事件 + 每种应有 payload 键 + `status`）、五组 `FROZEN_*` 冻结面 |
| **自扫描** | `scan_emit_sites()`：AST 扫全仓库的 `_emit(<字面量>, ...)` 调用点 |
| **对账** | `audit()`：声明 vs 实际，10 个字段全部机器可判定 |
| **能力** | `capabilities()`：前端据此显隐面板；**能推导的一律推导** |

自扫描用的是**与前端同款的技术**（AST 扫字面量），所以上游能自己发现
"前端会看不见什么"，而不必等前端来问。

### 21.2 只增不减（写进契约的规则）

前端对上新增自动跟上（新阶段自动多一个节点、新事件自动生成可读名字），
对**删除/改名**只能降级显示。所以：

| 改动 | 安全性 | 动作 |
|---|---|---|
| 加阶段 / 事件 / payload 键 / 工具 / 报告字段 | ✅ | 事件与 payload **必须补进 `EVENTS` 声明**（否则测试失败） |
| 删/改 事件 kind、阶段名、工具名、报告字段 | ❌ | 先标 `status="deprecated"` 保留**至少一个版本**，再升 `CONTRACT_VERSION`，并记进 CHANGELOG |

**"标了废弃却还在发"也被拦**：那是最坑的状态——前端会同时看到新旧两套。

### 21.3 两条硬约束（都是"前端扫不到"的坑）

1. **事件只能从 `CodingCycle._emit` 发出**。
   在别处 `append_event` 等于发了个**前端永远不认识的事件**（不在扫描范围）。
   实测确认：生产代码里 `append_event` 只有 `_emit` 一个调用点。
2. **kind 必须是字面量**。`_emit(kind_var, ...)` 前端 AST 扫不到——
   `audit()["nonliteral_kinds"]` 会点名。实测当前 12 个 kind 全是字面量。

### 21.4 暴露给前端

`GET /profile` 新增 `contract` 段（`describe()` + `audit()`）。
前端 bridge 可以直接读，不必再猜上游长什么样。实测：

```
contract.audit.ok = True   事件 12 种   工具 18 个   emit_files = ['core/coding_cycle.py']
```

### 21.5 顺带：能力声明

`capabilities()` 给前端"该不该显示某个面板"的依据。
`vision` 一项是**推导**的（`role_available("vision")`），不是手写 ——
前端 SPEC 里 `DEFAULT_SPEC` 那条教训就是手写兜底值会漂。
推不出来的（尚未实现）才显式 `False` 并附 `why`。

### 21.6 顺带修掉的文档漂移

`docs/OPERATIONS.md §8.2` 的回归清单表格**本身是坏的**：
7 行表格之后又跟了 3 行"5/6/7"，同号不同内容（正向链路、反向门禁、能力退化
被挤在表格外）。已合并为 11 行单一表格，并补入第 4 项"上游→前端契约未被破坏"。
同时把写死的"33/33"（实际已 35/35）改成"全部通过"。

## 22. 备份点自包含（备份机制自身的 bug）—— ✅ 已修

### 22.1 现象

`tests/backup.py` 的顺序原本是 **提交 → 写记录**。于是：

| 备份点 | 提交里包含的记录 |
|---|---|
| v1.4 @ `13f540c` | v1.**3** 的记录（v1.4 自己的记录还没写） |
| v1.5 | v1.4 的记录 |

后果很具体：按脚本打印的 `git reset --hard 13f540c` 回退到 v1.4，
**会丢掉 v1.4 自己的记录**——恰好是最需要它的时刻（想看清这个版本改了什么）。
平时看不出来，因为 `git status` 只是显示 VERSIONS.md 有一处未提交改动。

### 22.2 修法：把记录折进同一个提交

顺序改为 **提交代码 → 写记录 → `commit --amend`**：

```
[3/5] 提交代码        4a3e1c6
[4/5] 写记录          追加到 docs/VERSIONS.md
[5/5] 折进同一个提交  8723096  ← 备份点
```

现在 **一次备份 = 一次提交**，且该提交包含它自己的记录。

### 22.3 一个不能碰的坑：记录里不许写自己的 hash

第一版修法是"提交后回填 backup_ref"。**这会无穷回归**：
记录是提交内容的一部分 → 写进 hash 就改变 hash → 要再改一次 → 再变……

最终做法：记录里**不写自己的 hash**，改为

- 提交信息以 `{tag}:` 开头（本来就是这样）；
- 记录里写明定位命令 `git log --oneline --grep "^v1.5:"`。

tag 本身就是稳定的查找键，不需要自引用。

### 22.4 三条边界情况

| 情况 | 行为 |
|---|---|
| 第 3 步没有代码改动 | 不 amend（那会把记录折进**上一个**备份点），单独提交一条记录 |
| 工作区本来就干净 | 直接报告 HEAD，不产生空提交 |
| 上一次运行留下了未提交的 VERSIONS.md | 被 `git add -A` 一并收进本次提交（顺带自愈） |

### 22.5 验证

| 检查 | 结果 |
|---|---|
| v1.5 提交包含 `docs/VERSIONS.md`（自己的记录） | ✅ `git show --stat 8723096` 三文件：VERSIONS + backup.py + PENDING_DECISIONS |
| 提交后工作区干净 | ✅ `git status --short` 为空 |
| `git log --grep "^v1.5:"` 能定位 | ✅ 脚本第 5 步会把定位结果打印出来核对 |

## 23. 契约对账的**责任划分**（谁去改）—— ✅ 已落地

**起因**：你跟前端商定的机制是——定义契约，前端加一个运维机制，
后端服务起来后哪里对不上就**输出责任划分**，两边据此各做兼容。

§21 只做到了"什么算对不上"（`audit()`），没回答**谁来改**。
而这一步最容易走偏：前端也在做归因，两边各写一套必然分歧。

### 23.1 一条原则，其余都是它的展开

> **事实源在哪一侧，责任就在哪一侧。**

| 情况 | 归谁 |
|---|---|
| 上游发出/声明的东西与**上游自己的代码**不符 | **后端** |
| 上游已声明并正常发出，**前端不认识** | **前端** |
| 上游删/改了前端在用的东西**却没标废弃** | **后端**（破坏性变更没走流程） |
| 两边理解不同且**无法从事实源判定** | **双方协商** |

### 23.2 把规则**声明成表**，而不是写在注释里

`ISSUE_RULES`：21 条规则，每条带 `owner` / `severity` / `why` / `action`。
（**勘误**：本条原写"20 条"，实测为 21 条 = `U-` 7 + `P-` 14。见 §24.5。）
`code` 稳定（如 `P-version-behind`），可直接被前端的日志、工单、告警引用。

通过 `GET /profile` 的 `contract.responsibility` **暴露给前端**——
前端想离线归因就用这张表，不许自己发明。

### 23.3 `severity` 决定要不要拦（这条关系到"低定制"能不能成立）

| 级别 | 含义 | 前端 |
|---|---|---|
| `breaking` | 前端会真的看不到/画错 | 必须有人改 |
| `degraded` | 有兜底（降级显示）但要修 | 记日志，不阻断 |
| `info` | 多为 additive 新增 | 可不处理 |

**`info` 不参与 `verdict`。** 否则上游每加一个端点/工具，
前端都会被判成"有事要改"——"低定制"就又退化成"每次加东西都要两边同步改"。
这条有专门测试盯着（`info 级规则不参与 verdict`）。

### 23.4 两个刻意判成"需协商"的项

`P-event-gone-upstream`（前端把某事件当上游事件，上游没这声明）与
`P-version-unparsable`（版本号无法比较）——上游**单方面判不出来**：
前者不知道那事件历史上属不属于自己，后者本来就无法比较。
硬归给某一侧会把人带偏，所以标 `both`，`action` 写清两个分支。

### 23.5 三个调用口

| 接口 | 用途 |
|---|---|
| `GET /contract/check` | 上游自检（前端不必提交任何东西） |
| `POST /contract/check` | **完整对账 → 责任划分报告**（前端运维机制调这个） |
| `python -m core.contract [--peer x.json]` | 服务没起来时也能查 |
| `GET /profile` → `contract.responsibility` | 前端离线归因用规则表 |

`verdict` 五值：`ok` / `backend-action` / `frontend-action` /
`need-negotiation` / `multi-action`。

**启动自检**：上游在 `main.py` 导入时自查一次，**只有不通过时才打印一行**——
正常启动日志不该被"一切正常"占位。

### 23.6 顺带修的：`/` 的端点列表一直是手写的

`GET /` 原本返回 `["/run","/encode","/profile","/reflect","/decisions"]` ——
**漏了 `/skills`、`/candidates`**。而前端的运维机制要拿这份做端点对账，
所以它必须与真实路由一致。已改为从 `app.routes` **推导**（`_route_paths()`），
顺手也修掉了这处漂移。

### 23.7 测试发现的两个真问题（写测试时抓到的）

| 问题 | 说明 |
|---|---|
| **`P-schema-mismatch` 是死规则** | 定义了却没有任何分支会触发。已补：版本号"给了但看不懂"时触发 |
| **`P-version-unparsable` 级别定错** | 原本是 `info`，于是"版本对不上"时 verdict 仍是 `ok`——**整套对账的可信度都受影响，这不是 info**。已改 `degraded` |

顺带把测试里"自己重写一遍 verdict 判定"的写法改成**直接调 `compare()`** ——
否则测试测的是测试自己（这一版就是这么发现 `routes` 参数没传进去的）。

## 24. 采纳统筹契约：补 `ops` 与 `ops-action` —— ✅ 已落地

**背景**：统筹工作流（中间角色）给出了权威契约 `interface-contract.json`
v1.0.0 与两份**按侧拆分**的工作单。本仓库收到的后端工作单只有 **2 项**，
都是接口级（改词汇，不改模块划分）。

### 24.1 先说结论：21 条规则被原样采纳，零改判

统筹方的裁定是：**以上游 `core/contract.py` 的 `ISSUE_RULES` 为权威规则集，
归属与级别一条都没有改判**。被吸收的是 bridge 那侧的 17 条判定，
其中 8 条按边界改判为 `frontend` —— **那 8 条改的是 bridge 的代码，不是本仓库的**。

同时，契约把本仓库的 `PEER_FIELDS` 定为前端上报的**规范字段**
（`client_report_schema.canonical_fields`）。
这意味着那张规则表不再只是"我的实现细节"，而是**对外承诺**——
所以 §24.5 那条不变量检查不是锦上添花。

### 24.2 关键澄清：边界按**仓库**划，不按"服务"划

两侧对 "backend" 一词的所指原本不同（实测）：

| | 本仓库眼中的 backend | bridge 眼中的 backend |
|---|---|---|
| 含义 | 只有 `SimpleAgent2_Cycle` | **整个「服务」**= `bridge/spec.py` 的声明 + 上游代码 |

后果很具体：`bridge/spec.py` 里的声明类问题，bridge 判成 backend，
契约判成 **frontend**。**以契约为准：桥接层的声明问题算 frontend。**

这正是 §23 那条原则的具体化：**事实源在哪一侧，责任就在哪一侧** ——
声明与实现都在 `bridge/` 里，事实源就在 frontend 那侧。

### 24.3 本次实现（W-B1 + W-B2）

| 项 | 改动 |
|---|---|
| W-B1 归属词表 | 新增 `OWNER_OPS = "ops"`；`OWNER_ORDER` 四值且 **ops 排第一**；`compare()` 的 `counts` 与结果从三栏变**四栏**（新增顶层 `ops` 键） |
| W-B1 新增规则 | `O-service-down`（ops / breaking）、`O-frontend-not-built`（ops / breaking）；**action 文案取契约 `new_rules_required` 原文** |
| W-B2 结论词表 | `VERDICTS` 六值（补 `ops-action`）；**判定顺序：先判 ops** —— 服务不可达/前端没构建时后面一切结论都不成立 |
| 附带 | `describe()` 增 `owner_values` / `verdict_values` / `ops_fact_rules`，供统筹方的漂移检查比对两侧是否同词表 |

**为什么必须有 `ops` 这一栏**：没有它时，"服务没起来"只能被塞进 backend 或
frontend —— **归错人**。它跟双方契约都无关。

### 24.4 一个我自己拿的主意（已上报，等统筹方裁决）

`ops` 事实怎么进对账？契约把这 2 条规则的来源记为 `bridge: ops.service_down`，
但契约的 `client_report_schema`（= 我的 `PEER_FIELDS`，8 项）**没有 ops 字段**。

我**没有**自己往 `PEER_FIELDS` 里加一项 —— 那会让契约的 `canonical_fields`
当场过期（契约是只读资产，我不能改）。做法是区分两类东西：

| 类别 | 例子 | 进哪 |
|---|---|---|
| **声明**：前端"按什么写死的" | `phases` / `upstream_event_kinds` | `PEER_FIELDS`（契约已冻结的 8 项） |
| **观测**：运行态事实 | `service_down` / `frontend_not_built` | `POST /contract/check` 的并列字段 `ops`（不进 `PEER_FIELDS`） |

**分工**：`code` 与归属由上游规则表定义（单一词表），
**观测**由看得见环境的一侧上报 —— 上游在"服务活着"时无法观测"服务不可达"
（自己的不可达不可自证）。未知事实名一律忽略（additive 安全）。

### 24.5 修掉统筹方记的 F1 漂移，并让它不可能再发生

统筹方实测发现：`ISSUE_RULES` 是 **21** 条，而我的
`VERSIONS.md`(v1.7) / `PENDING_DECISIONS.md` / `CHANGELOG` 都写 **20** 条。

## 25. `ops.service_down` 通道语义确认（统筹方提出）—— ✅ 已落地

**背景**：统筹方复验 W-B1/W-B2 时**打接口实测**发现一条自相矛盾，记为
`ops_report_constraint`、状态 `AWAITING_SIDE_CONFIRMATION`，给了三个选项让我选。
本节的结论已按九节模板写成 `docs/EVALUATION-OPS-1.md`（含 C1–C8 自检）。

### 25.1 矛盾是什么

**`POST /contract/check` 能成功送达，就已经证明上游可达。**
所以随请求一起报上来的 `service_down=true` **不可能是此刻的状态**。
可它照样触发 `ops-action` —— 而 `ops-action` 的文案是"这一条修好之前后面都不成立"，
于是一条陈旧标志把后端/前端那些**本可修复**的结论全压掉了。

### 25.2 我选了哪条路：**选项 2 的语义 + 选项 1 的可见性**

统筹方倾向选项 1（只加 info、不改 verdict）。但我判断**选项 1 只买到可见性**，
它自己指出的危害（陈旧标志压掉全部结论）**仍在**。所以：

| 行为 | 实现 |
|---|---|
| **语义**（选项 2 的"标注为上次已知状态"分支） | `evidence` 带 `semantics: "last_known_state"`、`current: false`、`contradicted_by: "request_succeeded"` |
| **可见性**（选项 1 的机制） | 报告新增顶层 `warnings: []`，明说该标志与本请求可达性矛盾 |
| **判定修正**（两个选项都没解决的那点） | 被传输层证伪的事实**不驱动 `verdict`** |

判定修正的理由一句话：`ops` 优先的**前提**是"服务不可达时后面一切不成立"，
而请求成功把这个前提**证伪**了 —— 此时后面那些结论**是成立的**。

**为什么排除它不会漏掉真实故障**：真·服务不可达时前端**根本发不出这个请求**，
那种情况由 bridge 自己的本地自检负责，不依赖这条通道。
`frontend_not_built` 与可达性不矛盾（服务活着但前端没构建完全可能），**照旧驱动**。

### 25.3 守住的一条线：不改契约已固化的部分

`O-service-down` 的 **code / owner / severity 一个字都没动**（契约明示"原样采纳、零改判"），
规则表仍是 23 条。我只定义了**"它在什么条件下算当前值"** ——
那正是契约留白、明确等我确认的那一格。

**选项 2 的另一半（带时间戳的观测）我没做**：那要改 `ops` 的载荷形状，
而 `ops` 已进契约 `client_report_schema`，属接口级变更，必须走统筹方的变更流程。
已在评估文档里说明"若决定要，我可以实现"。

### 25.4 一个必须让前端知道的行为

只读 `verdict` 的消费方会看到 `ok`，从而**看不到**那条陈旧标志。
这是刻意的（它已非当前事实），而且**不是静默的**：它同时出现在 `ops` 栏与
`warnings` 里，`next` 也会追加一句"ops 栏有一条上次已知状态的标志未参与判定"。
评估文档 §6 把这条列为"最需要前端注意的一点"。

### 25.5 过程中发现并顺手加门禁的另一个问题：行尾被悄悄翻转

第一次 `git diff --stat` 显示 `core/contract.py` **1770 行**变更，而真实改动只有 60 行。
根因：`pathlib.Path.write_text()` 在 Windows 上把 `\n` 翻译成 `\r\n`，
我用一段 Python 脚本批量替换版本引用时**把该文件的 LF 整体翻成了 CRLF**
（本仓库行尾**本来就是混合的**：`core/*.py` 多为 LF，`README.md`/`CYCLE.md`/`docs/*.md` 多为 CRLF）。

已按字节恢复，并加成机械门禁（`test_doc_invariants.py` 第 9 组）：
**逐文件比对"工作区是否含 CRLF"与"HEAD 是否含 CRLF"**，不一致即 FAIL。
判据不引入新约定（不要求全仓统一），只要求"别悄悄改行尾"。
**已做负向测试确认它会抓**：临时翻转 `core/contract.py` → 退出码 1 → 按字节恢复。

**这条门禁在它被写出来的同一次改动里就抓到了第二例**：本轮升版本戳的脚本
（`Path.read_text` 在 Python 3.10 不支持 `newline=`，读的时候已经吃掉 `\r`，
写回就变成 LF）又把 5 个上游文档翻成了 LF —— 门禁报 FAIL，
我按字节逐个恢复。**两次都不是靠眼睛发现的。**

> **一个必须如实说明的发现**：本仓库"行尾混合"（`core/*.py` 是 LF，
> `README.md`/`CYCLE.md`/`docs/*.md` 是 CRLF）**不是原始设计，是我历轮脚本累积出来的** ——
> 升版本戳的脚本每轮把 5 个文档写回成 CRLF，`tests/backup.py` 追加 `VERSIONS.md`
> 时也是文本模式写（同理变 CRLF）。所以 HEAD 里的 CRLF 本身就是历史 churn 的产物。
>
> **没有在本轮顺手统一**：统一全仓行尾会让这个变更集的 diff 膨胀到无法评审
> （每个文档都整份变化），而这次的评审焦点是 `ops` 语义。
> 已列为待你拍板的一次性动作（见 `docs/PENDING_DECISIONS.md`）。
> 在那之前，门禁按"与 HEAD 一致"执行 —— 它防的是**悄悄改**，不是规定风格。

> 顺带修掉 `_cli()` 读 peer 文件不容忍 BOM 的问题（`utf-8-sig`）：
> PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会写 BOM，
> `json.load` 遇到它直接抛，而报错信息完全看不出是 BOM 问题。

## 27. 架构清单 A1b：`/contract/check` 自述权威范围 —— ✅ 已落地

**起因**：用户批准了架构级提案（原话「架构级别层面的按照你的想法执行吧，
写在清单里，我都批准了」）。统筹方拆成 A1–A5，其中落在我这一侧的只有
**A1b**：让 `/contract/check` 自述权威范围。

### 27.1 A1 的决定：切分职责，而不是合并入口

| 入口 | 权威范围 |
|---|---|
| `/contract/check`（本侧） | **跨侧对账**：归属、严重度、结论、`both` 协商项 |
| `/api/audit`（前端） | **本地自检**：bridge 自身声明 vs 实现 vs 环境 |

切分要成立，前提是**两侧各自声明自己管什么** ——
否则只是把"一个模糊的答案"变成"两个模糊的答案"。本项补的是本侧那一半。

**为什么切分比合并正确**（我认同统筹方的理由）：`/api/audit` 看得见本入口
**看不见**的东西（前端是否构建、钩子是否装上）—— 那些事实本来就无法由上游观测
（这一点是本侧在 §25 的 `EVALUATION-OPS-1` 里论证过的）。硬合并会丢掉这些观测能力。

### 27.2 实现

| 项 | 内容 |
|---|---|
| `AUTHORITY_SCOPE` | 自述 `id` / `role` / `covers` / `not_covers` / `rule_source` / `counterpart` / `policy`；**单一来源**，同时进 `/contract/check` 响应与 `/profile` 的 `contract` 段 |
| `not_covers` | **主动划出**本侧不该管的范围（本地环境细节 → `/api/audit`），不只是说"我管什么" |
| `responsibility_fingerprint()` | 规则表内容指纹，只覆盖 `code|owner|severity` |

**指纹的语义是刻意收窄的**：`why` / `action` 是**给人看的文案**，改它不该惊动消费方；
而**增删规则或改归属/级别**必须能被察觉。实测三态：

```
原指纹               740c48d2
改 why/action 后     740c48d2   ← 不变（只改文案）
改 owner 后          4ff7e560   ← 变了
恢复后               740c48d2   ← 回到原值
```

### 27.3 A1 验收里与我有关的两条

**① "一个测试：对同一跨侧不一致，两个入口给出的 owner 归属一致"**

`/api/audit` 在前端仓库，本侧调不到。所以我做的是**静态锚定版**：
拿契约的 `rule_crosswalk`（=两侧商定的统一映射）当锚点，
逐行断言本侧 owner == 契约 `unified_owner`。实测：

```
crosswalk 共 17 行；无上游等价（bridge 本地项）8 行
完整比对的: 8 行；部分等价（只比 owner）: 2 行
SPLIT（无可单判 owner）: ['backend.dead_event -> U-dead-event']
映射到本侧不存在的 code: 无     owner 不一致: 无     severity 不一致: 无
```

> **一个坑**：`upstream_equivalent` 是**带注释的自由文本** ——
> `"U-removed-surface (部分)"` / `"SPLIT"` / `"无（…）"`。
> 第一版直接拿去查表，误报 5 条"本侧缺失"。改成**取前导 code + 识别限定词**
> （部分等价只比 owner，`SPLIT` 只验 code 存在）后归零。
> 这与 §26 的教训同型：**检查器的第一版总是判据写宽了。**

**② "文档（两边）说明各自权威范围"** —— 本侧已写进
`docs/FRONTEND_CONTRACT.md` §6.6 与 `docs/MODULES.md` §23。

## 28. `P-phase-unknown` 改判 `both`/`degraded`（归因方向修正）—— ✅ 已落地

由前端在 `EVALUATION-ARCH-A1A-A4` §7-1 提出，统筹方裁定"**他们是对的**"。

### 28.1 原判错在哪

原来的判词是"前端在画一个上游没有的阶段 —— **上游删/改了阶段名**"，
归 `backend` / breaking。也就是说：**看到对端报了一个我没有的阶段，就推定是自己删的。**

实测那个阶段是 `manifest` —— **bridge 在 `write` 与 `check` 之间自补的门禁节点**。
后端从来没删过任何阶段。契约 `empirical_evidence.S2` 已在真实服务上打出这个错误：

```
[breaking] P-phase-unknown: 前端在画 `manifest`，上游没有
verdict = backend-action          ← 让【后端】去改
```

**「前端自造了一个节点」与「上游删了一个阶段」现象完全相同**，本侧只看得见
"对端报了一个我没有的阶段"，**方向判不出来**。契约 `boundary_definition` 明写
这种情形归 `both`。所以新判是 `both` / `degraded`：

```
改判前: backend-action          {'backend': 1, ...}
改判后: need-negotiation        {'both': 1, 'backend': 0, ...}
```

### 28.2 不因此丢失检测：`U-removed-surface` 兜住真正的删除

这是本次最要紧的一条论证。真正的"上游删了阶段"由
**`U-removed-surface`（backend / breaking）** 覆盖，而它与 `P-phase-unknown`
**判据完全不同**：

| | 判据 | 依赖对端上报？ |
|---|---|---|
| `U-removed-surface` | 拿**本侧冻结面**（`FROZEN_PHASES` 等）与**本侧当前代码**比对 | **不依赖** —— 本侧自查即得 |
| `P-phase-unknown` | 拿**对端报来的阶段**与本侧阶段集合比对 | 依赖 |

所以：**只要上游真的删了一个阶段，本侧自己就会报 `U-removed-surface`（backend/breaking）**，
无论前端报什么。改判 `P-phase-unknown` 只影响"看到未知阶段时怪谁"，
不影响"删除本身会不会被发现"。

已把它写成断言（`test_contract_attribution.py`）：

```
PASS  真正的删除场景由 U-removed-surface 覆盖（backend/breaking）
PASS  同一情形下 backend 栏必须为空（归因方向已修正）
```

### 28.3 这次最值得记的一点：绿的是测试，错的是判据

但那样就把一个**归因方向**的问题藏进了『验收通过』里。」这正是
`CHANGE-PROCESS` C7 想防的东西，而**我这边已经发生过一次**。

### 28.7 补记：契约 v1.0.7 还带了**方向判定树**（一并实现）

我上一轮在 `EVALUATION-ARCH-D1` §9 提了三个问题，其中第 3 个是
"`action` 里『先确认方向』这种写法是否可接受"。统筹方的回答不是口头答复，
而是**把它变成契约内容**：新增 `bridge_gate_steps` 字段 +

**是符合性门禁先发现它的**（`规范上报字段集合相等` 报红 —— 契约的
`canonical_fields` 从 9 项变 10 项）。如果没有那条门禁，我会漏掉这半个任务。

#### 树的内容（契约原文）

| 情形 | 方向 | 效果 |
|---|---|---|
| 1) 未知阶段 ∈ `peer.bridge_gate_steps` | **frontend**（bridge 自补节点被当阶段上报） | `action` 直接指名前端 |
| 2) ∈ 上游 `FROZEN_PHASES` 且 ∉ 当前 `PHASE_ORDER` | **backend**（上游删了冻结阶段） | 同时被 `U-removed-surface` 抓到 |
| 3) 其余 | **both** | 保持"先确认方向"，**不伪造方向** |

关键在于契约的 `effect_on_owner`：**owner 不变**（仍 `both`/`degraded`，
"避免来回改判"）。树**只用来锐化 `action` 文案**。

#### 实现：新增 `Issue.action_override`（只改文案的出口）

这带来一个结构问题：`Issue` 的 owner/severity 一向**全部来自规则表**，
而"方向"只能体现在文案上 —— 所以我给 `Issue` 加了一个 `action_override` 字段：

```python
"action": self.action_override or r.action,     # owner/severity 仍取 r
```

**刻意不允许逐条覆盖 owner/severity**。这不是省事，是为了守住一条纪律：
**归属只能有一处来源**（规则表 + 契约），否则"两个入口同一 owner"就无从保证。
已写成断言：`action_override 只改 action，owner/severity 仍来自规则表`。

方向本身用机器可读的 `evidence.direction` 暴露（`bridge_gate_step` /
`upstream_removed_frozen_phase` / `undetermined`）。

#### 一个我核过的边界：`failed`

`failed` 在 `FROZEN_PHASES` 里但不在 `PHASE_ORDER`，看似会命中情形 2。
**实际不会** —— 本规则的触发条件是"对端报的阶段 ∉ 全部 `CyclePhase` 值"，
而 `failed` 是 `CyclePhase` 成员，所以它根本不触发本条规则。
情形 2 只有在上游**真把某阶段从 `CyclePhase` 删掉**时才可达（那时判 backend 正确，
且 `U-removed-surface` 会同时报警）。已把它写成一对断言
（助手判情形 2 **且** peer 报 `failed` 不触发规则）。

#### 我另两个问题也被契约回答了

- **§9(2) severity 会不会被误读为"可以不修"** → 契约新增
  `response_contract.severity_consumer_obligation`：
  "**`degraded` 必须被呈现，不得被静默丢弃**"，并明确
  "**生产方不要因为担心被忽略而把 degraded 抬回 breaking**"。我保持 `degraded` 是对的。
- **§9(3) 指纹是否登记进契约** → 已登记进
  `response_contract.profile_additions`。

> 三个问题的回答方式很一致：**不靠口头承诺，靠写进契约并让机器可核**。

### 28.8 顺带修：行尾门禁自己把测试拖到超时

给 §25.5 那条行尾门禁写的第一版实现是**每个文件起一个 `git show` 进程**
（约 200 次子进程），本轮全量跑测试时**整个脚本超时**。

改法：换成**一次** `git ls-files --eol` —— 它直接给出 `i/`（索引）与 `w/`（工作区）
的行尾，既不用逐文件起进程，还顺带能抓 `w/mixed`（我自己那版抓不到）。

| | 第一版 | 现在 |
|---|---|---|
| 子进程数 | ~200 | 1 |
| 耗时 | >120 秒（超时） | **1.15 秒** |
| 覆盖面 | 只比对"是否含 CRLF" | 另抓 `mixed` |
| 断言 | 2 条 | 3 条（含防空转：扫到的文件数 > 50） |

> **教训**：**慢门禁等于会被绕过的门禁** —— 一个要跑两分钟的检查，
> 人迟早会不跑它。加检查时不仅要问"判据对不对"（§26/§27 的教训），
> 还要问"它会不会慢到没人愿意跑"。

## 29. 用户真实需求跑不通：五个缺陷（含"只能跑样例需求"的根因）—— ✅ 已修

**起因**：用户报告「只能跑样例需求，我刚才跑的需求是失败的」。
需求原文：**「读取一下你当前根目录下所有文件输出一个 txt 文本文档」**
（`demo=false`、`verify_command=''`，走前端 → bridge → 本仓库）。

定位过程：本仓库 `storage_data/` 里**没有**这次运行的记录 ——
它由前端以**独立运行根**启动（`SimpleAgent2_Cycle_VueWeb\data\`），
事件落在 `data\storage_data\runs\run_20260926_112631_e0b705\events.jsonl`。
从事件流重建出完整失败链，**五个缺陷全部在本仓库**：

### 29.1 ★ 缺陷一（根因）：manifest 只看得见 `.py`，任何非 Python 交付物必然失败

`check_manifest` 判断"声明的文件在不在"时**只在符号索引里查**，
而索引（`symbol_index.build_index`）只收 `.py`：

```
索引里的文件: ['add.py']          ← .txt 压根不在索引里
passed = False
  error declared-missing files_list.txt | 计划要产出 files_list.txt，但该文件不存在
```

**而那个文件其实已经写出来了**（`data\workspace\files_list.txt`，92 字节，
11:26:55 写入）。manifest 还是判"不存在" → cycle 直接 `phase=failed`。

**这就是"只能跑样例需求"的根因**：阶梯样本全产 `.py`，所以一路绿灯；
用户一要 txt 文档就 100% 失败 —— **与模型能力无关，是判据只覆盖了一半的文件类型**。

**修法**：声明文件先查符号索引（`.py` 走结构校验），**不在索引里就查磁盘**
（`_disk_fact()`：存在性 + size + sha1），存在即算交付。
顺带两条诚实化：
- 非 `.py` 却声明了 `symbols` → `warning symbols-unverifiable`（符号无法校验，但不静默通过）；
- `.py` 存在却没进索引（在 `_tmp/`、`.` 开头目录里）→ `warning not-indexed`。

### 29.2 ★ 缺陷二：整条人工决策路径 100% 不可用（且被文档承诺反着写）

`_ask()` 里：

```python
self._emit("decision_opened", ..., kind=kind)   # kind 与 _emit 的参数名同名！
```

`_emit` 的第一个参数**就叫 `kind`** → 调用点在**参数绑定阶段**就抛
`TypeError: _emit() got multiple values for argument 'kind'`，连函数体都进不去。
后果：

| 路径 | 状态 |
|---|---|
| 连续失败 → 问人（`repeated_failure`） | **100% 抛异常** |
| 回退前 → 问人（`risky_rollback`） | **100% 抛异常** |
| 前端装了 bridge 钩子时 | TypeError 把整轮 run 变成 `status=error`（用户那次就是这样） |

而 `_ask` 的 docstring 明写「**本方法不会抛异常**」——**文档承诺与实现相反**，
且这条路径**此前零测试覆盖**。

**修法**：payload 键 `kind` → `decision_kind`（这样对**任何**镜像我签名的钩子包装器都安全），
并把 `_emit` 的首参改名为 `event_kind` 做二次防御。
**新增机械门禁**（`test_frontend_contract.py` [2.5]）：AST 扫全部 `_emit` 调用点，
断言 payload 键不得与**位置绑定**的参数名（`event_kind` / `cycle_id`）相同
（`goal` 例外——它是签名里的记录字段）。扫 18 个调用点。
**新增运行时测试** `test_decision_path.py`（11 项）：直接调 `_ask` 断言
"不抛异常 + fail-safe 默认值 + 事件真的发出 + payload 键不撞参数名"。

### 29.3 缺陷三：`list_workspace` 把 `.git/` 里 **249 个文件**倒给模型

原来只过滤 `_` 开头的目录，而 `.git` 以 `.` 开头却不在过滤条件里 →
`dirs` 里保留了 `.git`，其内部文件（`COMMIT_EDITMSG` 等）不以 `.` 开头 → 全部列出。

后果不只是费 token：用户那次事件流里，模型**照单全收**，

**修法**：与 `core.symbol_index._SKIP_DIRS` **共用同一份跳过策略**（单一来源），

### 29.7 需要前端配合的一处（我改不了他们的代码）

`SimpleAgent2_Cycle_VueWeb\bridge\hooks.py` 的钩子包装器**镜像了 `_emit` 的签名**：

```python
def _emit(self, kind, cycle_id, goal="", **payload):
    ...
    return _orig_emit(self, kind, cycle_id, goal=goal, **payload)
```

参数名叫 `kind` → 任何 payload 键叫 `kind` 都会在它这里撞。
我这次从调用点去掉了 `kind`（缺陷二），所以**现状可用**；
但**结构上仍然脆弱**：将来任何一个 payload 键与它的参数同名都会重演。
**建议前端把包装器改成透传**：

```python
def _emit(self, *args, **kwargs):
    ...

```

## 33. `FIX-VERIFY-WIRING`：真实用户目标从不执行验证 —— ✅ 已修

**来源**：统筹方缺陷报告（含 `文件:行` 级定位 + 14 条运行史穷举），
评估文档 `docs/EVALUATION-FIX-VERIFY-WIRING.md`。

### 33.1 缺陷：一个 `if` 决定了两个能力是否存在

`main.py` 构造 `Orchestrator` 时没注入 `pipeline`，而唯一会注入它的
`_setup_orchestrator` 原先只在 **`if verify_command is not None:`** 成立时才被调用
（= 只有调用方自带验收命令时）。于是：

- **不带 `verify_command` 的真实目标永远不执行验证**
  → `memory.verify_state` 恒为 `None`；
- 最后却报「**缺少**可机器判定的验证命令」—— **而模型已经把命令拟好了**。
  **这个诊断是错的**，把定位带偏了整整一轮；
- **同一个 `if` 还连带杀掉了 `context_provider`（结构化上下文回流，§19 的能力）** ——
  这条统筹方没提，是我核出来的：`_setup_orchestrator` 注入的**三样**东西里，
  有两样依赖那个条件，所以用户那几次运行里**结构化上下文也从未生效**。

**这就解释了修完 §29 之后"样例过、用户需求仍然失败"的残余成因**：
样例手写了验收命令（走那条分支），用户目标没有。

### 33.2 我逐条复核了他们的证据（全部为真）

重点是他们指出的**我为什么抓不到**：`tests/diagnostics/repro_user_goal.py`
**手工传了** `pipeline=CheckPipeline()` → 于是它**永远复现不出**"生产忘了注入"。
**与 D7 同一个病根**（验证方式与生产路径不一致），**这是第二次**。

### 33.3 修法：治结构，不是治那一个调用点

| 改动 | 说明 |
|---|---|
| `coding_cycle.py` **两处** `if` 去掉 | 无条件 `_setup_orchestrator(verify_command)` —— pipeline 与 context_provider **总是**就位 |
| `main.py` | 顺手补 `pipeline=CheckPipeline()`，让 `/run`（无 cycle 层）也具备回流 |
| `_setup_orchestrator` | `verify_command is None` 时**保留原值**（见 §33.5 的回归） |
| `repro_user_goal.py` | **改走 `main._build_orchestrator()`**，不再手工注入 —— 否则这个脚本本身就是盲区 |

## 34. `VERIFY-VACUOUS`：自拟验收可以**恒真** —— `print('PASS')` 让"没做"也判成功 —— ✅ 已修

**来源**：统筹方缺陷报告（真实运行 `cy_20260926_154707_882595` + 机制定位 + 四条建议），
评估文档 `docs/EVALUATION-VERIFY-VACUOUS.md`。

> ⚠️ **这不是 `FIX-VERIFY-WIRING` 的回归** —— 是那条修复**唤醒**的一个原本睡着的洞。
> 它让"模型自拟的 verify"从**从不执行**变成**真的执行**（正确且必要），
> 于是执行结果第一次有了后果：`print('PASS')` 退出码 0 → 判成功。

### 34.1 缺陷：三个绿灯叠在一起，恰好等于"什么都没干"

目标「读取根目录下的项目结构输出一份分析报告」，调用方不给 `verify_command`：

| 事实 | 实测 |
|---|---|
| `manifest` 声明了几个交付件 | `declared=0` |
| `manifest` 硬校验跑了吗 | `checked=False`（note：*本轮没有声明文件清单，跳过硬校验*） |
| `check` 检查了什么 | `steps=0`（*本次 cycle 没有产生 .py 文件改动*） |
| 验证命令 | 模型自拟的 **`print('PASS')`** —— 恒真 |
| 结论 | **`phase=record`（成功）** |

而**根本没有产出那份报告**（工作区里只有上一次测试留下的文件）。

**机制**：`core/orchestrator.py` 采纳自拟 verify 时的**唯一**门槛是
"非空且可执行"。这与我们自己在同一文件里写的纪律直接冲突：
「调用方给出的验收标准是权威的：模型可以决定『怎么实现』，
但**绝不能改写『什么叫对』**」—— 调用方没给标准时，模型把"什么叫对"整个拿走了。

### 34.2 修法：给自拟判据一条**可机器判定**的下限

| 改动 | 说明 |
|---|---|
| `Orchestrator._deliverables()` | 本轮**可被判据引用**的交付物 = 计划声明 ∪ `write_file` 产物（**刻意不含** `prior_files` —— 那是历史文件） |
| `Orchestrator._verify_references()` | 命令引用了哪些交付物：**路径/文件名出现在文本里**，或**词干出现在代码里**（先 `tokenize` 剥掉字符串字面量，`print('add')` 因此不算引用） |
| `Orchestrator._model_verify_admissible()` | 两条下限：① 本轮**必须有交付物**（一份声明都没有就说不出"交付了什么"）② 命令**必须引用**其中至少一个 |
| 不合格时 | **不采纳**该命令（也**不清空**前几轮已采纳的好命令）→ 走已有的「未验证 → 显式失败」路径，错误文案说清是**判据不合格**而不是"缺少命令" |

**为什么判据选"引用交付物"**：`CHANGE-PROCESS.md` C2 要求每条主张可机器验证，
判据本身也一样。"命令里出现了某个交付物的路径/文件名/词干"是**字符串事实**；
"这条命令是不是恒真"在一般情况下**不可判定**。取一个可判定的下限，
胜过写一个看起来很聪明、实则判宽了的启发式。

**边界（刻意如此）**：这条只作用于**自拟**判据。调用方给了 `verify_command` 时，
验收标准是调用方的权威 —— 哪怕它写 `print('PASS')` 也照样通过。
把调用方的标准也拦下，就不是修 bug，是**夺权**。

### 34.3 附带三条（他们提的，都做了）

| # | 内容 |
|---|---|
| 附 1 | **`report.verify.source`**（`caller` / `model`）+ `verify` 事件加同名字段：两种来源的**可信度差很远**，而在这之前外部完全无法区分。它**只作事实**，不参与判定（判定只看退出码） |
| 附 2 | **每一次"判据被拒"都单独留痕**：`memory.verify_rejections` 只增不减，cycle 逐条发成 `verify_skipped` 事件（`reason` 里带**被拒命令原文**）。为什么不能只留最后一条 —— 实测那一轮里模型先给坏判据被拒、换一版好判据才通过；成功时把留痕清掉，事后就看不出"这次为什么多跑了两轮" |
| 附 3 | **`check` 阶段三态**：`checked` + `status ∈ {passed, failed, skipped}` 进 `CycleReport.check` 与日志（原来只报 `passed=True steps=0`，"没东西可查"与"查过并通过"同形，实测被读成绿灯） |
| 附 4 | **把"验证没执行"的两种原因分开**：`verify_wiring_http.py` 的第 2 条断言原为"`verify_passed` 非空"。`VERIFY-VACUOUS` 之后"没执行"多了一种**正确**原因（判据被拒），于是改成"非空 **或** 本轮判据被明确拒绝" —— 否则会把一次正确的拒绝读成 `FIX-VERIFY-WIRING` 的回归。**这是"验证自身的判据也要跟着改"的一个小例子** |

顺带补一条**上游文档漂移**：`core/contract.py` 的词表注释还写着"当前 12 种"，
而 `verify_skipped` 加进来后已是 **13** 种 —— 已改正。

### 34.4 上一轮的回归我这次没再犯（有意识地）

`VERIFY-VACUOUS` 的工具路径里，我**没有**把 `verify` 单独加成一个新事件，
而是复用 `verify_skipped`（理由：对外是同一类事实"本轮验证没跑，原因是…"）；
`report.verify.source` 与 `check` 都是 **additive** 键。
于是 `CONTRACT_VERSION` 仍 `1.1`、事件词表仍 **13** 种 —— 契约面只增不改名。

## B. 需要你拍板的策略（影响架构）

### B1 `需定` REVIEW 角色：仅建议，还是可否决

- **背景**：现有纪律里，模型审查**只能建议、不能否决**（防止幻觉变成硬门禁）。
  真正的门禁是程序化的 `CheckPipeline`（语法/lint/验证命令），它不会被模型改写。
- **技术前置**：`resolve_profile()` 仍是"两角色假设"，开启 REVIEW 前必须先清理，
  否则会出现"以为请了审查员，其实是同一个模型审自己"且**不报错**（README 限制 #4/#5）。
- **选项**：
  1. 审查仅作**建议**（建议）：结论进记忆和报告，不阻断流程；
  2. 审查可否决：模型说不行就停——**需要你先接受误报会拖慢流程**；
  3. 折中：审查可否决，但只对**白名单**的客观问题（如"声明的文件不存在"）。
- **建议**：先 1，积累几十轮样本后再考虑 3。

### B2 `默认: 不做` 数据库存储

- **背景**：你之前明确说"数据库接口预留，不实现"。现在 `storage_data/` 是本地文件
  （JSONL 事件 + 快照），`Storage` Protocol 已就位。
- **选项**：1. 维持现状（建议，默认）；2. 现在做 SQLite 实现；
  3. 只在需要跨机检索时才做。
- **影响**：做 DB 主要是为了**跨会话检索历史**与**并发**；单机单会话用不上。

### B3 `需定` 基准测试放哪（这条关系到纪律 7）

- **背景**：能力边界是 2/8，且在 `tests/bench/`。**benchmark 必须放在 agent 够不到的地方**，
  否则"自我迭代"会退化成"改考题"。
- **选项**：
  1. 移到仓库外的独立只读目录（建议）；
  2. 独立私有 git 库，只读挂载；
  3. 留在原处，靠纪律约束（**我不建议**，纪律挡不住自动化的自我优化）。
- **建议**：选 1 或 2。这条不做，B6（自我迭代）就不能开。

### B4 `需定` 备份频率与保留策略

- **背景**：现在每个里程碑一个 tag（v1.0 → v1.1），备份前强制跑全量测试，
  **验证不过就拒绝备份**，并自动写 `docs/VERSIONS.md` 记录。
- **选项**：
  1. 每完成一个变更集就备份一次（建议）——频率高，历史噪音大；
  2. 每小时/每次会话结束自动备份一次——**需要我加定时逻辑**；
  3. 维持每个里程碑一次；
  4. 在上面的基础上，加"保留最近 N 个"的清理策略（建议 N=20）。
- **建议**：1 + 4。你之前要求"备份频率拉高点"，1 比 3 密得多，但比 2 可控。

### B5 `需定` 模型路线：继续 7B，还是换更大模型

- **背景**：8 级阶梯实测 **2/8**（只过 L1、L4，都是自包含纯函数文件）。
  失败集中在**多文件协同、跨文件符号引用、长链路**。
- **关键判断**：当前瓶颈更像**模型能力**而不是流程。流程该修的我基本修了

- **选项**：
  1. **先换更大模型**（建议，如 14B/32B 或云端），看通过率抬到哪，

  2. 继续压 7B 的流程优化；
  3. 双轨：大模型跑主流程，7B 跑低风险子任务（省成本）。
- **建议**：选 1，用同一套 8 级阶梯做**对照实验**（阶梯本身不用改，这正好证明流程与模型解耦）。

## C. 技术缺口（等你排期；不需要你给外部资源）

### C1 `需排期` `fetch_url` 的 DNS rebinding

- **背景**：IP 字面量与 `localhost` 已拦截（含 20 个回归用例）；
  但域名在**请求时**被解析到内网仍拦不住——需要在传输层校验实际 peer IP。
- **风险**：只有在你让 agent 访问不可信 URL 时才被利用；当前工具主要用于读文档。
- **选项**：1. 做 peer-IP 校验；2. 直接禁用域名解析型抓取；3. 接受风险并记录。
- **建议**：1，但排在 B5 之后（优先级低于"能干活"）。

### C2 `默认: 不做` 子任务并行

- **背景**：多任务串行，延迟线性叠加。
- **不建议现在做的原因**：并行会引入共享工作区写冲突，在**正确性还没解决**（2/8）时
  增加并发只会让失败更难归因。

### ~~C3~~ `已完成` 压缩快照回流进 prompt

- **已做**（v1.2，过程见 `docs/CHANGELOG.md §19`）：`CodingCycle` 每轮决策前从事件流
  重算压缩快照 → 经 `Orchestrator.context_provider` 注入 prompt 的「结构化上下文」段。
- **守住的三条**：验证结论永远在最前且不被挤掉；该段有独立预算上限（预算的 1/3，≤1500 字符）；
  截断时明确写"已截断"。取快照任何环节抛异常都只降级为"无此段"，不影响主循环。
- **仍然存在的限制**（已记进 `README` 已知限制 #2）：预算上限偏保守，
  超长任务仍可能被截断，需要更大上下文窗口或调 `ORCH_*`。

### C4 `需排期` 工具的 `risk` / `stage` 声明

- **已完成**：`profiles` 过滤（`coding` 15 / `general` 4）。
- **仍缺**：`stage`（按阶段自动取工具，让 `tool_hint` 有强制力）、
  `risk`（高风险操作二次确认）。
- **建议**：先做 `stage`（纯收益）；`risk` 依赖 A2 的审批渠道，等通知通了再做。

### ~~C5~~ `已接线` `expected_output` 纳入校验

- **已做**（v1.2）：`Task.expected_output` 进入 `plan` 事件的 `intent`，
  被压缩成 `confidence=declared` 的事实，渲染在「计划声明（尚未确认为现实）」段。
- **为什么只到这一步**：它是**自由文本**（"可运行的 app.py"）。
  要做成**门禁**就必须让模型判断"是否达成"——那等于把幻觉源接进判据链，
